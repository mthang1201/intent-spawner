\section{Overview}
\label{sec:proposed_overview}

This chapter presents the design and formulation of the proposed method for intent- and context-aware notebook environment selection in JupyterHub on Kubernetes. The method addresses the challenge of translating an end user's natural-language workload description into an appropriate, policy-compliant computational environment without requiring manual exploration of container images, hardware resource envelopes, or platform configurations. The proposed system, designated as P2, is structured as a multi-stage recommendation and enforcement pipeline. Rather than delegating deployment decisions to an unconstrained generative model, the architecture strictly decouples semantic interpretation from infrastructure authority. Natural-language text is used exclusively to extract structured semantic facts, whereas candidate retrieval, feasibility filtering, ranking, and runtime binding operate strictly over a bounded, administrator-owned candidate catalog.

The overall operational transformation executed by the P2 pipeline can be expressed as a sequence of deterministic and inspectable transformations:
\[
x \longrightarrow I \longrightarrow (L_s, L_d) \longrightarrow L_f \longrightarrow F \longrightarrow c^* \longrightarrow \mathbf{e}^*,
\]
where $x$ denotes the untrusted natural-language workload request; $I$ represents the validated, normalized structured intent; $L_s$ and $L_d$ are the candidate shortlists generated by sparse lexical retrieval and dense semantic retrieval, respectively; $L_f$ is the fused candidate ranking produced by Reciprocal Rank Fusion; $F$ represents the feasible candidate subset remaining after deterministic hard constraint evaluation; $c^*$ is the top-ranked candidate identifier selected by deterministic preference ranking; and $\mathbf{e}^*$ is the authoritative spawn configuration resolved from the administrator-controlled catalog and enforced by the JupyterHub pre-spawn hook.

Figure~\ref{fig:p2_architecture} illustrates the end-to-end architecture of the proposed system, highlighting the modular decomposition and the clear separation of trust boundaries across functional components.

The P2 architecture organizes these operations across five distinct logical components structured along a feed-forward workflow. First, the Intent Interface and Extractor captures free-form workload descriptions and explicit user hints, parsing them into a strongly typed, schema-validated StructuredIntent contract ($I$). Next, the Candidate Catalog and Hybrid Retriever queries verified pairings of resource profiles and container images via parallel sparse lexical and dense semantic channels, generating candidate shortlists $L_s$ and $L_d$ that are subsequently fused into $L_f$ using Reciprocal Rank Fusion. The Constraint Evaluator and Deterministic Ranker then deterministically prunes candidates failing mandatory resource, accelerator, or capability constraints to establish the feasible candidate set $F$, subsequently ordering the remaining candidates through linear rank utility, soft user preferences, and resource cost efficiency to determine the top-ranked candidate $c^*$. Following candidate selection, the Policy Validator and Preview Runtime validates $c^*$ against authoritative administrator-governed allowlists and persists the decision as a time-limited preview state bound to an ephemeral, single-use cryptographic token. Finally, upon explicit user confirmation, the JupyterHub Pre-Spawn Integration Hook intercepts the notebook launch request, validates token provenance, and enforces the static container image and resource limits in KubeSpawner without performing runtime model inference. This component architecture ensures that recommendations remain advisory until explicitly approved by the user, and that the configuration applied to the Kubernetes Pod strictly matches the validated preview, preventing Time-of-Check to Time-of-Use (TOCTOU) discrepancies.

\section{Structured intent representation}

Natural-language workload descriptions exhibit high semantic variability, combining general computational descriptions, software preferences, and strict hardware constraints. Treating these heterogeneous elements uniformly within an unstructured query string creates an undesirable coupling between uncertain language interpretation and strict operational enforcement. To resolve this challenge, P2 introduces an intermediate structured data contract designated as StructuredIntent. The StructuredIntent contract acts as an immutable boundary between natural language understanding and candidate ranking. It structures extracted workload properties into functional dimensions: task categories, required features, preferred features, forbidden features, required frameworks, preferred frameworks, required libraries, preferred libraries, explicit resource constraints, ambiguity diagnostics, normalized query text, and extraction provenance metadata. The distinction between required and preferred attributes is central to the system's correctness. A required feature or framework is treated as a strict feasibility condition that must be demonstrated by candidate metadata; failure to satisfy a required attribute results in immediate candidate pruning. In contrast, a preferred feature represents a non-mandatory user affinity that contributes positively to the soft ranking score of candidates that have already satisfied all mandatory requirements. Table~\ref{tab:structured_intent_schema} outlines the schema specification and validation rules governing the \texttt{StructuredIntent} data model.

Algorithm~\ref{alg:intent_normalization} formalizes the structured intent extraction, normalization, and validation procedure. It guarantees that raw natural-language inputs and explicit UI parameters are deterministically canonicalized into an immutable, schema-compliant contract prior to candidate retrieval.

\begin{algorithm}[ht]{Structured intent extraction, normalization, and validation procedure}
\label{alg:intent_normalization}
\begin{algorithmic}[1]
\Require Raw user request string $x$, explicit UI parameters $H_{\mathrm{user}} = \langle \mathrm{min\_cpu}, \mathrm{min\_ram}, \mathrm{dataset\_size}, \mathrm{gpu} \rangle$
\Ensure Validated, immutable structured intent contract $I$
\State $I_{\mathrm{raw}} \gets \operatorname{ExtractSemantics}(x)$ \Comment{Structured LLM parser or regex fallback}
\State $I_{\mathrm{norm}} \gets \operatorname{CanonicalizeUnicodeAndText}(I_{\mathrm{raw}})$
\State $I_{\mathrm{norm}}.\mathrm{req\_feats} \gets \operatorname{DeduplicateAndSort}(I_{\mathrm{norm}}.\mathrm{req\_feats})$
\State $I_{\mathrm{norm}}.\mathrm{pref\_feats} \gets \operatorname{DeduplicateAndSort}(I_{\mathrm{norm}}.\mathrm{pref\_feats}) \setminus I_{\mathrm{norm}}.\mathrm{req\_feats}$ \Comment{Required takes precedence}
\If{$I_{\mathrm{norm}}.\mathrm{req\_feats} \cap I_{\mathrm{norm}}.\mathrm{forbid\_feats} \neq \emptyset$}
    \State \Return \textbf{error}(\texttt{InvalidContract: Contradictory required and forbidden features})
\EndIf
\State $R \gets \operatorname{OverrideResourceConstraints}(I_{\mathrm{norm}}.\mathrm{resource\_constraints}, H_{\mathrm{user}})$ \Comment{UI hints override extracted values}
\State $I \gets \operatorname{FreezeContract}(I_{\mathrm{norm}}, R, \text{schema\_version}=\text{"1.0.0"})$
\State \Return $I$
\end{algorithmic}
\end{algorithm}

Prior to candidate retrieval, all textual and categorical fields within the structured intent undergo systematic normalization. The system executes Unicode Normalization Form KC (NFKC) conversion, collapses consecutive whitespace, and applies case-folding. Semantic collections, including framework and library names, are deduplicated and lexicographically sorted. This canonicalization ensures that superficial formatting variations in user prompts do not alter recommendation behavior (e.g., canonicalizing \texttt{"Scikit-Learn"}, \texttt{"scikit\_learn"}, and \texttt{" scikit-learn "} to identical internal representations). Furthermore, contradictory specifications are resolved deterministically: if a capability is declared as both required and preferred, the required classification takes precedence, whereas overlapping required and forbidden attributes trigger an immediate contract validation error. Explicit numerical values supplied directly through the user interface are granted strict precedence over quantities inferred from free-form text. If a user specifies a dataset size of 4.0~GB in a numeric input field, this value is adopted authoritatively as $I.\mathrm{dataset\_size\_gb}$, overriding ambiguous textual references.

The structured intent extractor is strictly constrained to emit semantic descriptions of the workload rather than infrastructure configuration directives. Specifically, the schema forbids the inclusion of Kubernetes resource objects, raw container image registries, or arbitrary profile names. This architectural boundary reduces the attack surface and prevents natural language prompts from injecting unauthorized deployment configurations or arbitrary container specifications. The system incorporates dual extraction mechanisms: an external structured extraction interface (e.g., supported by large language models) and a deterministic, regex-based local fallback extractor. When an external extraction service experiences network failure, timeout, or emits malformed output, the system automatically degrades to deterministic local extraction. The provenance of the extraction mode is recorded in the \texttt{extraction\_provenance} metadata field and preserved throughout the recommendation trace for auditing.

\section{Hybrid candidate retrieval}

\subsection{Dual-channel candidate retrieval pipeline}

To operationalize candidate discovery over the administrator catalog $C$, the P2 recommendation engine deploys a dual-channel hybrid retriever combining complementary sparse lexical and dense semantic pathways. Figure~\ref{fig:p2_retrieval_pipeline} depicts the data flow and component interactions of this retrieval and rank fusion stage.

\begin{figure}[ht]{Hybrid candidate retrieval pipeline combining sparse lexical and dense semantic channels with Reciprocal Rank Fusion}
\centering
\includegraphics[width=0.98\textwidth]{figures/figure_3_2_hybrid_retrieval_pipeline.pdf}
\label{fig:p2_retrieval_pipeline}
\end{figure}

The two retrieval mechanisms execute in parallel:
\[
L_s = \operatorname{BM25}(q_s, C), \quad L_d = \operatorname{Dense}(\phi(I), C),
\]
where $q_s$ is the synthesized sparse lexical query constructed from the structured intent, $\phi(I)$ is the dense vector embedding of the intent, and $L_s$ and $L_d$ are the resulting ranked candidate shortlists.

\subsection{Sparse lexical query construction and execution}

The sparse retrieval module applies BM25 to index and search candidate environment documents, configured with standard hyperparameters $k_1 = 1.5$ and $b = 0.75$.

The key mechanism of this stage is the deterministic transformation of the validated \texttt{StructuredIntent} $I$ into an expanded lexical query $q_s$. Rather than passing only the raw natural-language prompt $x$, the query builder synthesizes a structured lexical string by aggregating multiple semantic fields:
\[
\begin{aligned}
q_s = \operatorname{Concat}\Big( & x, \, I.\mathrm{normalized\_query}, \, \operatorname{Tokens}(I.\mathrm{task\_types}), \\
& \operatorname{Tokens}(I.\mathrm{req\_frameworks} \cup I.\mathrm{pref\_frameworks}), \\
& \operatorname{Tokens}(I.\mathrm{req\_libs} \cup I.\mathrm{pref\_libs})\Big).
\end{aligned}
\]
Query $q_s$ undergoes NFKC normalization, lowercasing, punctuation stripping, and token deduplication. Executing $q_s$ against the candidate corpus yields an ordered list $L_s$ ranked by BM25 score, ensuring that exact technical keywords (such as specific library names, framework identifiers, and API terms) are matched with high fidelity.

\subsection{Dense semantic indexing and query inference}

The dense retrieval channel captures conceptual semantic affinities when user phrasing differs from catalog keywords. Candidate documents $c \in C$ are mapped offline into a continuous embedding space using a pre-trained transformer model (\texttt{all-MiniLM-L6-v2}), producing normalized vectors $\phi(c) \in \mathbb{R}^D$ serialized into an immutable index artifact.

At recommendation time, the normalized structured intent $I$ is encoded into query embedding $\phi(I) \in \mathbb{R}^D$. Dense retrieval computes the cosine similarity between $\phi(I)$ and candidate vectors $\phi(c)$, yielding an ordered candidate list $L_d$ sorted by descending semantic similarity.

\subsection{Reciprocal rank fusion implementation}

To synthesize rankings from sparse and dense channels without relying on uncalibrated raw score interpolation, P2 implements Reciprocal Rank Fusion (RRF). For each candidate $c \in \mathcal{C} = \operatorname{Candidates}(L_s) \cup \operatorname{Candidates}(L_d)$, the fused score is defined as:
\[
\operatorname{RRF}(c) = \sum_{m \in \{s, d\}} \mathbb{I}(c \in L_m) \cdot \frac{w_m}{k_{\mathrm{RRF}} + \operatorname{rank}(c, L_m)},
\]
where $k_{\mathrm{RRF}} = 60.0$, and channel weights are set to $w_s = 1.0$ and $w_d = 1.0$.

Algorithm~\ref{alg:rrf_fusion} details the fusion and shortlist truncation procedure. The fused ranking is truncated to a top-$K$ candidate shortlist $L_f$ ($K = 10$), which is subsequently passed to deterministic constraint evaluation. Score ties among candidates are broken deterministically by ascending alphanumeric candidate identifier.

\begin{algorithm}[ht]{Reciprocal Rank Fusion for hybrid candidate retrieval}
\label{alg:rrf_fusion}
\begin{algorithmic}[1]
\Require Ranked sparse list $L_s$, ranked dense list $L_d$, fusion constant $k_{\mathrm{RRF}}$, weights $w_s, w_d$, shortlist capacity $K$
\Ensure Fused candidate shortlist $L_f = (c_{(1)}, c_{(2)}, \dots, c_{(K)})$
\State $\mathcal{C} \gets \operatorname{Candidates}(L_s) \cup \operatorname{Candidates}(L_d)$
\For{each candidate $c \in \mathcal{C}$}
    \State $\operatorname{RRF}(c) \gets \sum_{m \in \{s, d\}} \mathbb{I}(c \in L_m) \cdot \frac{w_m}{k_{\mathrm{RRF}} + \operatorname{rank}(c, L_m)}$
\EndFor
\State $L_f \gets \operatorname{TopK}\Big(\mathcal{C}, K, \text{key} = c \mapsto (-\operatorname{RRF}(c), c)\Big)$ \Comment{Descending score, alphanumeric tie-breaker}
\State \Return $L_f$
\end{algorithmic}
\end{algorithm}

\section{Deterministic constraint evaluation}

Following candidate retrieval, every candidate in shortlist $L_f$ is evaluated against mandatory technical constraints. A hard constraint represents an uncompromising operational condition: if a candidate fails even a single constraint, it is immediately pruned regardless of its retrieval score.

Formally, let $h_j(I, c) \in \{0, 1\}$ represent the binary compliance outcome of the $j$-th hard constraint predicate for candidate $c$ under structured intent $I$. The overall feasibility predicate $H(I, c)$ is defined as their logical conjunction:
\[
H(I, c) = \prod_{j=1}^{J} h_j(I, c).
\]
A candidate $c$ is deemed feasible if and only if $H(I, c) = 1$. The feasible candidate set $F$ is defined as:
\[
F = \left\{ c \in L_f \mid H(I, c) = 1 \right\}.
\]

Table~\ref{tab:hard_constraints_spec} summarizes the hard constraint rules, mathematical predicates, operational enforcement conditions, and diagnostic error codes. Figure~\ref{fig:p2_constraints_flow} illustrates the sequential pruning decision tree executed for each candidate.

Hardware accelerator, CPU, and memory requirements are enforced through strict binary boundary predicates:
\[
h_{\mathrm{GPU}}(I, c) = \mathbb{I}(I.\mathrm{gpu\_requirement} \neq \texttt{required} \lor c.\mathrm{has\_gpu} = \text{true}),
\]
\[
h_{\mathrm{CPU}}(I, c) = \mathbb{I}(c.\mathrm{cpu\_limit} \ge I.\mathrm{min\_cpu}),
\]
\[
h_{\mathrm{RAM}}(I, c) = \mathbb{I}(c.\mathrm{mem\_limit} \ge I.\mathrm{min\_ram} \land c.\mathrm{mem\_limit} > I.\mathrm{dataset\_size\_gb}).
\]
If an intent specifies a mandatory GPU, any CPU-only candidate is strictly pruned. Similarly, profile memory limits must satisfy both the requested minimum memory and exceed the declared dataset size, preventing immediate runtime Out-Of-Memory (OOM) pod terminations.

Software capabilities and architectural constraints undergo set-theoretic verification against candidate catalog declarations:
\[
h_{\mathrm{caps}}(I, c) = \mathbb{I}(I.\mathrm{req\_feats} \subseteq c.\mathrm{capabilities}) \cdot \mathbb{I}(I.\mathrm{forbid\_feats} \cap c.\mathrm{capabilities} = \emptyset).
\]
P2 adopts a conservative metadata policy: if a candidate does not explicitly declare a required capability in its verified catalog record, the capability is treated as absent. Semantic proximity in embedding space is never accepted as a substitute for unadvertised software packages or drivers.

A central design property of P2 is treating an empty feasible set $F = \emptyset$ as a valid, first-class system outcome. When constraint evaluation determines that no retrieved candidate satisfies all mandatory requirements, the system does not relax constraints or guess an alternative environment. Instead, P2 halts execution and returns an explicit \texttt{no\_feasible\_candidate} result. The user interface displays the specific constraints that caused infeasibility (e.g., missing GPU availability or dataset size exceeding profile limits). The user is prompted to refine their workload description or manually select an administrator-allowlisted profile. This defensive design converts silent under-provisioning errors into visible, actionable feedback.

\section{Deterministic candidate ranking}

\subsection{Multi-Criteria deterministic scoring formulation}

All feasible candidates $c \in F$ are evaluated by a multi-criteria scoring function balancing retrieval relevance, soft user preferences, and resource cost efficiency. The ranking score $S(c) \in [0, 1]$ is formulated as:
\[
S(c) = w_{\mathrm{ret}} \cdot U(r_f(c)) + w_{\mathrm{pref}} \cdot S_{\mathrm{pref}}(I, c) + w_{\mathrm{res}} \cdot (1.0 - \operatorname{Cost}(c)),
\]
where $U(r_f(c))$ denotes the linear rank utility derived from fused retrieval rank $r_f(c)$, $S_{\mathrm{pref}}(I, c) \in [0, 1]$ measures soft preference alignment, and $\operatorname{Cost}(c) \in [0, 1]$ represents the candidate's normalized resource footprint. The weights are configured as:
\[
w_{\mathrm{ret}} = 0.60, \quad w_{\mathrm{pref}} = 0.25, \quad w_{\mathrm{res}} = 0.15,
\]
satisfying $w_{\mathrm{ret}} + w_{\mathrm{pref}} + w_{\mathrm{res}} = 1.00$.

\subsection{Linear rank utility and resource cost modeling}

The rank utility function $U(r)$ converts ordinal retrieval positions into a linear prior:
\[
U(r) = \max\left(0.0, \, 1.0 - \delta_{\mathrm{rank}} \cdot (r - 1)\right),
\]
where the rank decay parameter $\delta_{\mathrm{rank}} = 0.10$. Each retrieval rank drop incurs a constant score penalty of $w_{\mathrm{ret}} \cdot \delta_{\mathrm{rank}} = 0.60 \times 0.10 = 0.06$. This linear formulation enables exact quantification of promotion distance: soft preferences alone ($w_{\mathrm{pref}} = 0.25$) can promote a candidate by up to four ranks ($0.25 / 0.06 \approx 4.17$), while combined preference and resource efficiency ($0.25 + 0.15 = 0.40$) can promote a highly suitable candidate from rank~7 to rank~1.

The resource cost metric $\operatorname{Cost}(c)$ formalizes the systems principle of minimal sufficiency: among multiple feasible candidates, the platform prefers the candidate with the smallest resource envelope, conserving cluster capacity for concurrent tenants \cite{k8sresources,resourcecentral}:
\[
\operatorname{Cost}(c) = \frac{\alpha_{\mathrm{cpu}} \cdot \frac{c.\mathrm{cpu}}{\max \mathrm{CPU}} + \alpha_{\mathrm{ram}} \cdot \frac{c.\mathrm{ram}}{\max \mathrm{RAM}} + \alpha_{\mathrm{gpu}} \cdot \frac{c.\mathrm{gpu}}{\max \mathrm{GPU}}}{\alpha_{\mathrm{cpu}} + \alpha_{\mathrm{ram}} + \alpha_{\mathrm{gpu}}},
\]
where weights are set to $\alpha_{\mathrm{cpu}} = 1.0$, $\alpha_{\mathrm{ram}} = 1.0$, and $\alpha_{\mathrm{gpu}} = 2.0$, reflecting accelerator scarcity.

Algorithm~\ref{alg:deterministic_ranking} formalizes candidate evaluation, multi-criteria scoring, and tie-breaking. Rather than re-evaluating individual constraint conditions, the algorithm delegates feasibility verification to the constraint evaluator $\operatorname{IsFeasible}(I, c)$. Deterministic tie-breaking is enforced by sorting candidates using a four-element total order: descending score ($-S(c)$), ascending resource cost ($\operatorname{Cost}(c)$), ascending retrieval rank ($r$), and ascending lexicographical candidate identifier.

\begin{algorithm}[ht]{Deterministic candidate evaluation, multi-criteria scoring, and tie-breaking}
\label{alg:deterministic_ranking}
\begin{algorithmic}[1]
\Require Fused candidate shortlist $L_f$, structured intent $I$, weights $(w_{\mathrm{ret}}, w_{\mathrm{pref}}, w_{\mathrm{res}})$, rank decay $\delta_{\mathrm{rank}}$
\Ensure Recommended candidate identifier $c^*$ (or $\emptyset$ if no candidate is feasible)
\State $\mathcal{F} \gets \emptyset$
\For{each candidate $c \in L_f$}
    \If{$\neg \operatorname{IsFeasible}(I, c)$}
        \State \textbf{continue} \Comment{Prune candidate violating hard constraints}
    \EndIf
    \State $r \gets \operatorname{rank}(c, L_f)$
    \State $U(r) \gets \max\big(0.0, \, 1.0 - \delta_{\mathrm{rank}} \cdot (r - 1)\big)$
    \State $S(c) \gets w_{\mathrm{ret}} \cdot U(r) + w_{\mathrm{pref}} \cdot S_{\mathrm{pref}}(I, c) + w_{\mathrm{res}} \cdot (1.0 - \operatorname{Cost}(c))$
    \State $\mathcal{F} \gets \mathcal{F} \cup \{\langle c, S(c), \operatorname{Cost}(c), r \rangle\}$
\EndFor
\If{$\mathcal{F} = \emptyset$}
    \State \Return $\emptyset$ \Comment{Trigger \texttt{no\_feasible\_candidate} outcome}
\EndIf
\State $c^* \gets \operatorname{ArgMin}_{c \in \mathcal{F}} \big(-S(c), \, \operatorname{Cost}(c), \, r, \, c\big)$ \Comment{Deterministic 4-key total order}
\State \Return $c^*$
\end{algorithmic}
\end{algorithm}

\section{JupyterHub integration and runtime enforcement}

\subsection{Trusted candidate resolution and policy validation}
\label{subsec:policy_validation}

The candidate identifier $c^*$ produced by the ranking engine is not directly executable. Before any configuration can be presented to the user, $c^*$ must be resolved against the authoritative administrator catalog and verified by the \texttt{PolicyValidator}.

The policy validation layer enforces six mandatory assertions: (1)~the recommended profile identifier exists in the active profile allowlist; (2)~the recommended image identifier exists in the active container image allowlist; (3)~the resolved image reference matches the catalog's digest-pinned reference exactly; (4)~the active policy version matches the deployed platform version; (5)~the candidate catalog checksum matches the provenance record; and (6)~the recommendation data structure strictly satisfies the deployment schema.

This multi-layer validation establishes an impermeable trust boundary between recommendation logic and infrastructure execution. Even in the event of an upstream retrieval or model anomaly, the validator prevents unapproved images or arbitrary resource configurations from reaching Kubernetes.

\subsection{Two-phase preview and confirmation lifecycle}
\label{subsec:preview_workflow}

To guarantee human agency and operational safety, recommendations are presented through an interactive preview workflow. Figure~\ref{fig:p2_preview_lifecycle} details the sequence of interactions across the user, backend, preview runtime, policy validator, and JupyterHub.

\begin{figure}[ht]{Two-phase preview, user confirmation, and pre-spawn binding lifecycle}
\centering
\includegraphics[width=0.98\textwidth]{figures/figure_3_3_preview_spawn_lifecycle.pdf}
\label{fig:p2_preview_lifecycle}
\end{figure}

The preview workflow operates in two phases:
\begin{itemize}
    \item \textbf{Phase 1 (Preview Generation):} The authenticated user submits a workload description. The backend resolves the top candidate, validates policy compliance, and stores a stateful preview record encapsulating an ephemeral preview token (UUIDv4), authenticated username, timestamp, a time-to-live (TTL) expiration boundary of 1800 seconds (30 minutes), and recommended profile and image parameters. The UI renders the proposed environment, resource limits, and explanation.
    \item \textbf{Phase 2 (Confirmation and Binding):} The user reviews the recommendation. If the prompt is edited, the token is invalidated. Upon explicit confirmation (or manual override), the preview token is submitted with the spawn request, consumed atomically, and used to configure the notebook server.
\end{itemize}

\subsection{Pre-spawn binding hook and zero-recomputation execution}
\label{subsec:prespawn_binding}

An essential architectural property of the integration is zero-recomputation execution during notebook spawning. In standard KubeSpawner deployments, single-user notebook servers are launched via asynchronous spawn forms. P2 intercepts this lifecycle using a synchronous \texttt{pre\_spawn\_hook}.

Algorithm~\ref{alg:prespawn_enforcement} presents the pre-spawn token verification, policy allowlist validation, and deterministic resource binding procedure.

\begin{algorithm}[ht]{JupyterHub pre-spawn policy validation and deterministic resource binding}
\label{alg:prespawn_enforcement}
\begin{algorithmic}[1]
\Require Spawner instance $spawner$, catalogs $(\mathcal{P}, \mathcal{I})$, preview store $\mathcal{S}_{\mathrm{previews}}$
\Ensure Configures $spawner$ parameters authoritatively or aborts spawn
\State $\langle token, user, action \rangle \gets \operatorname{ExtractSubmissionOptions}(spawner)$
\State $item \gets \operatorname{ValidatePreview}(\mathcal{S}_{\mathrm{previews}}, token, user)$ \Comment{Validates token existence, user binding, and TTL}
\If{$action \notin \{\text{"accept"}, \text{"override"}\}$}
    \State \textbf{abort}(\texttt{"Invalid recommendation decision action"})
\EndIf
\State $\langle profile, image \rangle \gets \operatorname{ResolveAllowlistedEntities}(item, \mathcal{P}, \mathcal{I})$
\State $\operatorname{ConsumeToken}(\mathcal{S}_{\mathrm{previews}}, token)$ \Comment{Single-use consumption prevents replay}
\State $\operatorname{ApplyResourceConfiguration}(spawner, profile)$ \Comment{Inject CPU/RAM limits and guarantees}
\State $spawner.\mathrm{image} \gets image.\mathrm{digest\_reference}$ \Comment{Immutable digest reference}
\State $\operatorname{AttachAuditAnnotations}(spawner, item)$
\end{algorithmic}
\end{algorithm}

When JupyterHub triggers Pod creation, the pre-spawn hook intercepts execution before the Kubernetes Pod manifest is submitted to the cluster API. The hook extracts the preview token, verifies user provenance and expiration, validates allowlist membership, and applies the CPU and memory guarantees, limits, and digest-pinned image reference to the spawner attributes. Structured audit annotations (such as event ID, selected profile, and image) are attached to the Pod metadata.

Importantly, the pre-spawn hook performs zero model inference, zero natural language parsing, and zero candidate ranking. This zero-recomputation property eliminates Time-of-Check to Time-of-Use (TOCTOU) inconsistencies: because the hook retrieves the exact confirmed decision record rather than re-evaluating the recommendation at spawn time, the environment instantiated on Kubernetes is guaranteed to match the configuration validated and accepted by the user. Furthermore, isolating inference from the spawn critical path ensures that pod startup latency remains fast, deterministic, and protected against external model service outages.
