\section{Overview}
\label{sec:proposed_overview}

This chapter describes the design and formal model of our intent- and context-aware environment selector for JupyterHub on Kubernetes. In multi-tenant clusters, data scientists often struggle to choose the right container image and resource allocation. They must navigate dozens of software stacks, GPU configurations, and CPU/memory limits without knowing exactly what their code needs. Our system, named P2, automates this selection from free-form natural language. 

We base P2 on a straightforward design principle: language models interpret user intent, but deterministic rules control infrastructure. Letting a generative model write Kubernetes Pod manifests directly is dangerous. Models hallucinate package names, produce invalid resource requests, and cannot guarantee policy compliance. Instead, P2 confines language understanding to semantic extraction. Downstream retrieval, constraint pruning, scoring, and pod configuration operate strictly over an administrator-approved candidate catalog.

Formally, P2 maps an incoming request to an authoritative deployment through a chain of deterministic stages:
\[
x \longrightarrow I \longrightarrow (L_s, L_d) \longrightarrow L_f \longrightarrow F \longrightarrow c^* \longrightarrow \mathbf{e}^*,
\]
where $x$ is the raw natural-language query; $I$ is the validated, schema-compliant intent contract; $L_s$ and $L_d$ denote candidate shortlists from sparse lexical and dense semantic search; $L_f$ is the merged ranking from Reciprocal Rank Fusion; $F$ is the feasible subset surviving hard constraint checks; $c^*$ represents the top candidate chosen by multi-criteria ranking; and $\mathbf{e}^*$ is the concrete Kubernetes configuration applied at spawn time.

Figure~\ref{fig:p2_architecture} shows the end-to-end architecture of P2 and the trust boundary between recommendation logic and runtime execution.

The pipeline consists of five core components arranged in a feed-forward workflow:
\begin{enumerate}
    \item \textbf{Intent Interface and Extractor:} Parses the user prompt $x$ and any manual UI hints into a typed \texttt{StructuredIntent} object ($I$).
    \item \textbf{Candidate Catalog and Hybrid Retriever:} Indexes verified image-profile pairings. It queries them across parallel sparse (BM25) and dense (vector embedding) channels, producing shortlists $L_s$ and $L_d$, which fuse into $L_f$.
    \item \textbf{Constraint Evaluator and Deterministic Ranker:} Prunes any candidate that violates mandatory GPU, CPU, memory, or software requirements to form the feasible set $F$. It then scores the survivors using retrieval rank, user preferences, and resource cost to select $c^*$.
    \item \textbf{Policy Validator and Preview Runtime:} Checks $c^*$ against cluster allowlists. If valid, the system creates a time-limited preview record identified by a single-use token.
    \item \textbf{JupyterHub Pre-Spawn Hook:} Intercepts the final notebook launch. It verifies the preview token and binds the confirmed container image and resource limits into KubeSpawner.
\end{enumerate}
This workflow keeps recommendations advisory. Users retain full control to inspect, confirm, or override the chosen environment before any pod starts.

\section{Structured intent representation and local NLP extraction pipeline}
\label{sec:structured_intent_extraction}

\subsection{Problem formulation: Structured information extraction and slot-filling}
\label{subsec:intent_problem_formulation}

Free-form workload requests are inherently unstructured, ambiguous, and noisy. A user query submitted to an interactive computing hub frequently juxtaposes high-level scientific goals (``train a deep vision model on satellite imagery''), concrete software requirements (``using PyTorch and timm, but without TensorFlow''), and physical hardware constraints (``requires at least 16\,GB of RAM and a GPU''). Passing such unstructured natural-language strings directly into candidate retrieval or Kubernetes controllers couples probabilistic language understanding with authoritative infrastructure orchestration. 

To break this coupling and establish a formal trust boundary, we formulate user intent processing as a structured \textit{Information Extraction (IE) and Slot-Filling} problem \cite{jurafsky2023slp}. Formally, given a raw user request string $x \in \mathcal{X}$, an optional source code context $x_{\mathrm{code}} \in \mathcal{X}_{\mathrm{code}}$ (such as imported packages in a notebook cell), and explicit user-specified form parameters $H_{\mathrm{user}} = \langle \mathrm{min\_cpu}, \mathrm{min\_ram}, \mathrm{dataset\_size}, \mathrm{gpu} \rangle$, the extraction task maps the input tuple to an immutable, schema-validated contract $I \in \mathcal{I}$:
\begin{equation}
\label{eq:intent_contract}
x, x_{\mathrm{code}}, H_{\mathrm{user}} \xrightarrow{\quad\text{Extract \& Normalize}\quad} I = \Big\langle \mathcal{T}, \mathcal{F}_{\mathrm{req}}, \mathcal{F}_{\mathrm{pref}}, \mathcal{F}_{\mathrm{forbid}}, \mathcal{L}_{\mathrm{req}}, \mathcal{L}_{\mathrm{pref}}, \mathcal{M}_{\mathrm{req}}, \mathcal{M}_{\mathrm{pref}}, g, r_{\mathrm{cpu}}, r_{\mathrm{mem}}, d_{\mathrm{data}}, q_{\mathrm{norm}}, \pi \Big\rangle,
\end{equation}
where:
\begin{itemize}
    \item $\mathcal{T} \subseteq \mathcal{T}_{\mathrm{all}}$ represents the subset of classified scientific task categories (\textit{e.g.}, \texttt{Model Training}, \texttt{Deep Learning}, \texttt{Data Analysis}, \texttt{Model Inference}, \texttt{Visualization}), providing semantic context for downstream retrieval.
    \item $\mathcal{F}_{\mathrm{req}}, \mathcal{F}_{\mathrm{pref}}, \mathcal{F}_{\mathrm{forbid}}$ denote mutually disjoint sets of required, preferred, and forbidden system-level capabilities (\textit{e.g.}, CUDA user-space drivers, JupyterLab extensions).
    \item $\mathcal{L}_{\mathrm{req}}, \mathcal{L}_{\mathrm{pref}}$ denote domain frameworks (\textit{e.g.}, PyTorch, TensorFlow, Apache Spark).
    \item $\mathcal{M}_{\mathrm{req}}, \mathcal{M}_{\mathrm{pref}}$ denote domain libraries and tools (\textit{e.g.}, pandas, Polars, scikit-learn, XGBoost).
    \item $g \in \{\texttt{required}, \texttt{preferred}, \texttt{forbidden}, \texttt{unspecified}\}$ defines the resolved accelerator modality.
    \item $r_{\mathrm{cpu}} \in \mathbb{R}^+ \cup \{\bot\}$, $r_{\mathrm{mem}} \in \mathbb{R}^+ \cup \{\bot\}$, and $d_{\mathrm{data}} \in \mathbb{R}^+ \cup \{\bot\}$ denote quantitative slot values for minimum CPU cores, minimum system memory in gigabytes, and declared dataset size in gigabytes, respectively ($\bot$ denotes an unconstrained slot).
    \item $q_{\mathrm{norm}}$ denotes the canonicalized lexical query string used for sparse text retrieval.
    \item $\pi = \langle \text{extractor\_id}, \text{version}, \text{model\_id}, \text{hash} \rangle$ encapsulates provenance metadata, guaranteeing cryptographic traceability.
\end{itemize}

A critical design requirement of the schema is the strict operational partition between \textit{mandatory requirements} and \textit{soft preferences}. A required attribute (\textit{e.g.}, an entity in $\mathcal{L}_{\mathrm{req}}$ or $g = \texttt{required}$) represents an absolute feasibility precondition; any candidate environment lacking that capability is pruned by hard constraint filtering. In contrast, a preferred attribute (\textit{e.g.}, an entity in $\mathcal{L}_{\mathrm{pref}}$ or $g = \texttt{preferred}$) reflects user affinity without excluding viable environments, contributing instead to multi-criteria rank promotion. Crucially, the schema contains \textit{zero} fields for Kubernetes primitives, container registries, or network policies, establishing a structural barrier against privilege escalation. \subsection{The local deterministic NLP extraction architecture}
\label{subsec:local_nlp_pipeline}

To fulfill this extraction contract without introducing external network dependencies or runtime non-determinism, P2 implements a local, specialized Natural Language Processing pipeline. Rather than relying on ungrounded heuristic rules or raw regular expressions, the local extractor employs a staged information extraction pipeline structured into five deterministic phases:

\textbf{1. Multilingual Text Normalization and Clause-Level Tokenization:}
Raw queries are first normalized using Unicode NFKC (Normalization Form Compatibility Composition) to unify accented characters, eliminate decomposition artifacts, and resolve compatibility ligatures. Text undergoes lowercasing, whitespace collapsing, and punctuation normalization while preserving hyphens within technical identifiers (\textit{e.g.}, \texttt{"scikit-learn"}). 

The normalized string is subsequently partitioned into an ordered sequence of proposition spans $\mathcal{S} = (s_1, s_2, \dots, s_K)$ via a cross-lingual clause tokenizer. Boundary segmentation relies on orthographic punctuation delimiters (\texttt{[.;!?\textbackslash n]+}) and adversative discourse markers across both English and Vietnamese (\textit{e.g.}, \textit{but, however, whereas, yet, except for, instead of, nhưng, tuy nhiên, song, thay vì, loại trừ}). In natural language, modal operators and negation scopes are strictly bounded by clause boundaries \cite{jurafsky2023slp,morante2012modality}. By isolating clauses prior to entity evaluation, the tokenizer prevents negation in one propositional span (\textit{e.g.}, \textit{``strictly avoid TensorFlow''}) from corrupting affirmative requirements in adjacent spans (\textit{e.g.}, \textit{``train with PyTorch''}).

\textbf{2. Domain-Specific Gazetteer and Scientific Stack Ontology:}
Entity identification is grounded in a curated, versioned Data Science Stack Ontology $\mathcal{O}$. Each ontological entry $e = \langle c, k, \text{kind}, \mathcal{S}_f, \mathcal{A}_{\mathcal{T}} \rangle$ maps a canonical concept $c$ to its technical domain $k$ (\textit{e.g.}, Deep Learning, Tabular Engineering, Machine Learning, Visualization), architectural role (\texttt{framework}, \texttt{library}, or \texttt{feature}), surface alias forms $\mathcal{S}_f$, and associated task categories $\mathcal{A}_{\mathcal{T}}$. For example, the PyTorch concept registers surface forms $\{\texttt{"pytorch"}, \texttt{"torch"}, \texttt{"torchvision"}, \texttt{"torchaudio"}\}$ and aliases such as $\texttt{"th"} \to \texttt{"pytorch"}$.

To achieve high-throughput lexical scanning without false positives, the gazetteer compiles surface forms into regularized Deterministic Finite Automata (DFA) with lookaround boundary assertions. The recognizers explicitly avoid technical collision; for example, the matcher for TensorFlow alias \texttt{"tf"} employs negative lookahead to prevent false triggers on \texttt{"tf-idf"} (\texttt{\textbackslash b tf(?!\textbackslash s*[-/]?\textbackslash s*idf)\textbackslash b}). Furthermore, the pipeline automatically filters out all standard Python library modules via \texttt{sys.stdlib\_module\_names} to suppress spurious dependencies. When source code context $x_{\mathrm{code}}$ is provided, the extractor parses Python import statements (\textit{e.g.}, \texttt{"import torch as th"}) directly via AST analysis, registering verified imports as ground-truth required dependencies $\mathcal{L}_{\mathrm{req}}$ with maximal confidence.

\textbf{3. Contextual Negation Scope Detection and Modality Governance:}
For each ontological entity detected within a clause $s_k$, the pipeline performs directional syntactic cue governance to assign an operational modality:
\begin{equation}
\operatorname{Modality}(e, s_k) \in \{\textsc{Forbidden}, \textsc{Required}, \textsc{Preferred}, \textsc{Mention}\}.
\end{equation}
The scope resolver scans the propositional span for bilingual modality cues:
\begin{itemize}
    \item \textit{Negation Cues} $\mathcal{C}_{\mathrm{neg}}$ (\textit{e.g.}, \textit{strictly avoid, without, no need for, never, do not use, forbid, không cần, tuyệt đối không, cấm, tránh, loại bỏ}) assign $\textsc{Forbidden}$ to any entity in their immediate governing window \cite{morante2012modality}.
    \item \textit{Requirement Cues} $\mathcal{C}_{\mathrm{req}}$ (\textit{e.g.}, \textit{require, must have, mandatory, need, essential, cần, bắt buộc, yêu cầu, phải có}) assign $\textsc{Required}$.
    \item \textit{Preference Cues} $\mathcal{C}_{\mathrm{pref}}$ (\textit{e.g.}, \textit{prefer, would like, nice to have, optional, ideally, recommend, ưu tiên, thích, nếu có thể, khuyến khích}) assign $\textsc{Preferred}$.
\end{itemize}
The pipeline enforces strict monotonic modality precedence: $\textsc{Forbidden} \succ \textsc{Required} \succ \textsc{Preferred} \succ \textsc{Mention}$. If an entity is marked forbidden in any clause, it is unconditionally excised from $\mathcal{F}_{\mathrm{req}}, \mathcal{F}_{\mathrm{pref}}, \mathcal{L}_{\mathrm{req}},$ and $\mathcal{L}_{\mathrm{pref}}$, preventing contradictory constraints from reaching downstream components. A specialized accelerator analyzer similarly evaluates global GPU cues, classifying $g$ into \texttt{forbidden} (\textit{e.g.}, \textit{``cpu-only'', ``thuần cpu'', ``without gpu''}), \texttt{required}, or \texttt{preferred}.

\textbf{4. Quantitative Resource Slot-Filling and Unit Normalization:}
Resource requirements are parsed through multilingual quantitative slot-filling patterns. Numeric expressions for CPU cores (\textit{e.g.}, \textit{``at least 8 cores'', ``tối thiểu 4 vCPU''}) are extracted as floating-point lower bounds $r_{\mathrm{cpu}}$. Memory requirements (\textit{e.g.}, \textit{``requires 16GB RAM'', ``bộ nhớ 8 GiB''}) and dataset volume expressions (\textit{e.g.}, \textit{``dataset size is 12GB'', ``dữ liệu khoảng 4.5 GB''}) are parsed with automatic unit conversion, standardizing megabytes to gigabytes ($m_{\mathrm{gb}} = m_{\mathrm{mb}} / 1024.0$). 

To ensure human oversight, an authoritative override hierarchy is applied: explicit user-selected form values $H_{\mathrm{user}}$ deterministically supersede any text-inferred values ($H_{\mathrm{user}} \succ \operatorname{Extract}(x)$). For instance, if a user specifies 8.0\,GB in the interface form, this value binds authoritatively to $d_{\mathrm{data}}$, overriding any ambiguous number mentioned in the prose.

\textbf{5. Confidence-Weighted Task Classification and Contract Freezing:}
Task categories $\mathcal{T}$ are inferred via a dual-evidence mechanism: (1) action keyword rules weighted by empirical confidence scores $w \in [0, 1]$ (\textit{e.g.}, \textit{``fine-tuning''} $\to 1.0$ for \texttt{Model Training}, \textit{``dataframes''} $\to 0.85$ for \texttt{Data Analysis}, \textit{``trực quan hóa''} $\to 0.95$ for \texttt{Visualization}), accepting tasks whose aggregate confidence satisfies $\tau \ge 0.70$; and (2) ontological entity linkages, whereby validated frameworks automatically register their inherent task associations (\textit{e.g.}, PyTorch registers \texttt{Deep Learning} and \texttt{Model Training}). 

Finally, the extractor validates schema invariants ($(\mathcal{F}_{\mathrm{req}} \cup \mathcal{L}_{\mathrm{req}}) \cap \mathcal{F}_{\mathrm{forbid}} = \emptyset$), compiles the canonical query string $q_{\mathrm{norm}}$, and computes a cryptographic SHA-256 digest over the ontology version, parser configuration, and extracted values. The contract is frozen into an immutable \texttt{StructuredIntent} instance $I$.

Algorithm~\ref{alg:intent_normalization} formalizes this deterministic local NLP extraction and validation procedure.

\begin{algorithm}[ht]{Deterministic local NLP information extraction and contract validation procedure}
\label{alg:intent_normalization}
\begin{algorithmic}[1]
\Require Raw query text $x$, code context $x_{\mathrm{code}}$, UI hints $H_{\mathrm{user}}$, Domain Ontology $\mathcal{O}$
\Ensure Validated, immutable structured intent contract $I$
\State $x_{\mathrm{norm}} \gets \operatorname{NFKC\_Normalize}(x)$, \quad $\mathcal{S} \gets \operatorname{ClauseSegment}(x_{\mathrm{norm}})$ \Comment{Segment on punctuation \& discourse cues}
\State $\mathcal{L}_{\mathrm{code}} \gets \operatorname{ExtractPythonImports}(x_{\mathrm{code}}) \setminus \text{STDLIB}$ \Comment{Ground-truth code import analysis}
\State $\mathcal{F}_{\mathrm{req}} \gets \emptyset, \, \mathcal{F}_{\mathrm{pref}} \gets \emptyset, \, \mathcal{F}_{\mathrm{forbid}} \gets \emptyset, \, \mathcal{L}_{\mathrm{req}} \gets \mathcal{L}_{\mathrm{code}}, \, \mathcal{L}_{\mathrm{pref}} \gets \emptyset$
\For{each clause $s_k \in \mathcal{S}$}
    \For{each entity match $e = (c, k) \in \operatorname{GazetteerScan}(s_k, \mathcal{O})$}
        \State $m \gets \operatorname{ResolveModalityScope}(s_k, e)$ \Comment{Directional cue analysis: Negation/Requirement/Preference}
        \If{$m = \textsc{Forbidden}$}
            \State $\mathcal{F}_{\mathrm{forbid}} \gets \mathcal{F}_{\mathrm{forbid}} \cup \{c\}$
            \State Evict $c$ from $\mathcal{F}_{\mathrm{req}}, \mathcal{F}_{\mathrm{pref}}, \mathcal{L}_{\mathrm{req}}, \mathcal{L}_{\mathrm{pref}}$ \Comment{Monotonic precedence: Forbidden overrides all}
        \ElsIf{$m = \textsc{Preferred}$ \textbf{and} $c \notin \mathcal{F}_{\mathrm{forbid}}$}
            \State Assign $c$ to $\mathcal{F}_{\mathrm{pref}}$ or $\mathcal{L}_{\mathrm{pref}}$ according to ontological kind $k$
        \ElsIf{$m \in \{\textsc{Required}, \textsc{Mention}\}$ \textbf{and} $c \notin \mathcal{F}_{\mathrm{forbid}}$}
            \State Assign $c$ to $\mathcal{F}_{\mathrm{req}}$ or $\mathcal{L}_{\mathrm{req}}$ according to ontological kind $k$
        \EndIf
    \EndFor
\EndFor
\State $g \gets \operatorname{AnalyzeGPUModality}(x_{\mathrm{norm}}, \mathcal{S})$ \Comment{Detect GPU requirement or forbidden CPU-only cues}
\State $\langle r_{\mathrm{cpu}}, r_{\mathrm{mem}}, d_{\mathrm{data}} \rangle \gets \operatorname{SlotFillResources}(x_{\mathrm{norm}}, \mathcal{S})$ \Comment{Quantitative parsing with unit normalization}
\State $\langle r_{\mathrm{cpu}}, r_{\mathrm{mem}}, d_{\mathrm{data}}, g \rangle \gets \operatorname{ApplyUIOverrides}(\langle r_{\mathrm{cpu}}, r_{\mathrm{mem}}, d_{\mathrm{data}}, g \rangle, H_{\mathrm{user}})$ \Comment{UI hints take absolute precedence}
\State $\mathcal{T} \gets \operatorname{ClassifyTasks}(x_{\mathrm{norm}}, \mathcal{O}, \tau = 0.70)$ \Comment{Confidence-weighted action matching \& ontology propagation}
\If{$(\mathcal{F}_{\mathrm{req}} \cup \mathcal{L}_{\mathrm{req}}) \cap \mathcal{F}_{\mathrm{forbid}} \neq \emptyset$}
    \State \Return \textbf{error}(\texttt{InvalidContract: Contradictory required and forbidden entities})
\EndIf
\State $\pi \gets \operatorname{ComputeProvenanceDigest}(\mathcal{O}, \mathcal{F}_{\mathrm{req}}, \mathcal{L}_{\mathrm{req}}, \dots)$ \Comment{Cryptographic SHA-256 provenance signature}
\State $I \gets \operatorname{FreezeContract}(\mathcal{T}, \mathcal{F}_{\mathrm{req}}, \mathcal{F}_{\mathrm{pref}}, \mathcal{F}_{\mathrm{forbid}}, \mathcal{L}_{\mathrm{req}}, \mathcal{L}_{\mathrm{pref}}, g, r_{\mathrm{cpu}}, r_{\mathrm{mem}}, d_{\mathrm{data}}, x_{\mathrm{norm}}, \pi)$
\State \Return $I$
\end{algorithmic}
\end{algorithm}

\subsection{Computational efficiency and controller footprint guarantees}
\label{subsec:nlp_runtime_characteristics}

The architectural design of the local NLP extraction pipeline satisfies four strict systems engineering criteria required for enterprise Kubernetes deployments:

\begin{enumerate}
    \item \textbf{Sub-5ms Execution Latency:} Because all gazetteer recognizers and syntactic pattern matchers are pre-compiled into regularized finite-state automata, text parsing executes in linear time $O(|x| + |\mathcal{O}|)$ with respect to query length and ontology vocabulary. In empirical cluster benchmarks (detailed in Section~\ref{subsec:e1_recommendation_quality}), the local pipeline achieves a mean execution latency of $2.28$\,ms per request. This represents an approximate $660\times$ speedup compared to external LLM API invocations (which average $1,508$\,ms due to wide-area network round trips and generative token decoding).
    \item \textbf{100\% Deterministic Reproducibility:} Large language models inherently exhibit stochastic variability due to temperature sampling and token probability distributions. In contrast, our local NLP pipeline contains zero non-deterministic components: identical input text $x$ and ontology $\mathcal{O}$ produce bit-for-bit identical \texttt{StructuredIntent} objects across infinite runs. This deterministic repeatability is crucial for administrative auditing, debugging, and security compliance.
    \item \textbf{Zero Controller Footprint Bloat:} In a Kubernetes environment, the JupyterHub Controller (or KubeSpawner operator pod) executes as a centralized cluster control component with tight resource quotas. Embedding deep neural networks, large multi-billion parameter foundation models, or heavy PyTorch/Transformer runtime libraries directly into the controller would bloat container image sizes by 5 to 15\,GB and require several gigabytes of dedicated host memory. This creates severe memory ballooning and elevates the risk of fatal Out-Of-Memory (OOM) evictions that could crash the entire multi-tenant controller. In contrast, our local NLP pipeline requires only the standard Python runtime and lightweight compiled data structures, incurring a trivial memory footprint ($< 2$\,MB RAM overhead) and adding zero external system dependencies.
    \item \textbf{Dual-Backend Operational Resilience:} While P2 supports an optional remote LLM-assisted backend for conversational parsing, the local NLP extractor serves both as a fully autonomous zero-cost offline engine and as an instantaneous, zero-downtime fallback. If an external model experiences network partitioning, API throttling, or malformed schema returns, P2 switches instantly to the local extractor without user disruption. The active backend is permanently recorded in \texttt{extraction\_provenance} for end-to-end auditability.
\end{enumerate}

\subsection{Retrieval pipeline architecture}
\label{subsec:retrieval_architecture}

Relying solely on keywords fails when users describe tasks informally. Conversely, relying solely on vector embeddings often misses exact package names and version tags. We therefore deploy a dual-channel hybrid retriever that combines sparse lexical search with dense semantic search in parallel (Figure~\ref{fig:p2_retrieval_pipeline}).

The two retrieval channels execute concurrently:
\begin{equation}
L_s = \operatorname{BM25}(q_s, C), \quad L_d = \operatorname{Dense}(\phi(I), C),
\end{equation}
where $q_s$ is an expanded lexical query constructed from the intent, $\phi(I)$ is the dense vector embedding of $I$, and $L_s, L_d$ are the resulting ranked candidate shortlists.

\subsection{Sparse lexical and dense semantic retrieval channels}
\label{subsec:sparse_dense_channels}

\textbf{Sparse Lexical Channel:} The sparse channel utilizes the BM25 probabilistic relevance framework \cite{bm25} configured with standard saturation and length normalization parameters ($k_1 = 1.5, b = 0.75$). Rather than querying raw user prose alone, the query synthesizer constructs an expanded lexical representation $q_s$ by aggregating normalized intent attributes:
\begin{equation}
\begin{aligned}
q_s = \operatorname{Concat}\Big( & x, \, I.\mathrm{normalized\_query}, \, \operatorname{Tokens}(I.\mathrm{task\_types}), \\
& \operatorname{Tokens}(I.\mathrm{req\_frameworks} \cup I.\mathrm{pref\_frameworks}), \\
& \operatorname{Tokens}(I.\mathrm{req\_libs} \cup I.\mathrm{pref\_libs})\Big).
\end{aligned}
\end{equation}
Query $q_s$ undergoes case-folding, NFKC canonicalization, and punctuation stripping. Evaluating candidate catalog $C$ with $q_s$ yields candidate shortlist $L_s$, ensuring exact lexical matching over critical technical identifiers such as package names, build tags, and specific framework APIs.

\textbf{Dense Semantic Channel:} The dense channel captures contextual semantic intent when user formulations deviate linguistically from catalog descriptors. During catalog preparation, candidate documents $c \in C$ are embedded offline into dense vectors $\phi(c) \in \mathbb{R}^D$ ($D = 384$) using the pre-trained \texttt{all-MiniLM-L6-v2} bi-encoder model \cite{sentencebert}. The resulting candidate representations are compiled into an immutable index artifact.

At query time, the system encodes the normalized intent contract $I$ into query vector $\phi(I) \in \mathbb{R}^D$. It then computes cosine similarities between $\phi(I)$ and pre-computed candidate vectors $\phi(c)$:
\begin{equation}
\operatorname{Sim}(\phi(I), \phi(c)) = \frac{\phi(I) \cdot \phi(c)}{\|\phi(I)\|_2 \, \|\phi(c)\|_2},
\end{equation}
returning shortlist $L_d$ sorted in descending order of semantic similarity.

\subsection{Rank fusion via Reciprocal Rank Fusion (RRF)}
\label{subsec:rank_fusion}

Sparse BM25 scores (unbounded in $[0, \infty)$) and dense cosine similarities (bounded in $[-1, 1]$) exhibit disparate numerical scales and non-linear score distributions. Blending raw scores via linear combinations is inherently brittle, requiring continual empirical hyperparameter tuning across differing corpus sizes. P2 overcomes this limitation by implementing Reciprocal Rank Fusion (RRF) \cite{rrf}. For every candidate $c \in \mathcal{C} = \operatorname{Candidates}(L_s) \cup \operatorname{Candidates}(L_d)$, the fused reciprocal score is defined as:
\begin{equation}
\operatorname{RRF}(c) = \sum_{m \in \{s, d\}} \mathbb{I}(c \in L_m) \cdot \frac{w_m}{k_{\mathrm{RRF}} + \operatorname{rank}(c, L_m)},
\end{equation}
where $k_{\mathrm{RRF}} = 60.0$ is the standard ranking smoothing constant validated in information retrieval literature \cite{rrf}, and channel weights are balanced equally ($w_s = 1.0, w_d = 1.0$).

Algorithm~\ref{alg:rrf_fusion} details how candidate lists are aggregated, sorted, and truncated into a top-$K$ shortlist $L_f$ ($K = 10$). Score ties are broken deterministically by sorting candidate IDs in alphanumeric order.

\begin{algorithm}[ht]{Reciprocal Rank Fusion for hybrid candidate retrieval}
\label{alg:rrf_fusion}
\begin{algorithmic}[1]
\Require Ranked sparse list $L_s$, ranked dense list $L_d$, fusion constant $k_{\mathrm{RRF}}$, weights $w_s, w_d$, shortlist capacity $K$
\Ensure Fused candidate shortlist $L_f = (c_{(1)}, c_{(2)}, \dots, c_{(K)})$
\State $\mathcal{C} \gets \operatorname{Candidates}(L_s) \cup \operatorname{Candidates}(L_d)$
\For{each candidate $c \in \mathcal{C}$}
    \State $\operatorname{RRF}(c) \gets \sum_{m \in \{s, d\}} \mathbb{I}(c \in L_m) \cdot \frac{w_m}{k_{\mathrm{RRF}} + \operatorname{rank}(c, L_m)}$
\EndFor
\State $L_f \gets \operatorname{TopK}\Big(\mathcal{C}, K, \text{key} = c \mapsto (-\operatorname{RRF}(c), c)\Big)$ \Comment{Descending score, alphanumeric tie-breaker}
\State \Return $L_f$
\end{algorithmic}
\end{algorithm}

\subsection{Architectural justification: Why hybrid retrieval and constraint filtering over direct LLM generation?}
\label{subsec:architectural_justification}

A natural alternative design for natural-language environment selection would be to prompt an advanced Large Language Model directly: feeding the user prompt and catalog description into an LLM context window and instructing the model to generate the target image name, resource profile, or Kubernetes Pod manifest. While superficially simpler to construct, such end-to-end generative coupling violates fundamental principles of safe systems engineering. We justify P2's multi-stage hybrid retrieval and deterministic constraint architecture across five foundational pillars:

\begin{enumerate}
    \item \textbf{Closed-World Allowlist vs.\ Open-Ended Hallucination:} 
    Production Kubernetes infrastructure operates as a strictly closed physical environment: physical worker nodes possess fixed CPU and memory capacities, physical accelerators belong to specific hardware generations (e.g., NVIDIA Ampere vs.\ Turing), and container runtimes can only execute images that exist in trusted enterprise registries with cryptographic digest signatures \cite{oci}. In contrast, generative language models operate under an unconstrained generative distribution $P(\text{manifest} \mid x)$ over arbitrary token sequences. Generative models are inherently susceptible to hallucination \cite{ji2023hallucination}, frequently generating non-existent container image tags (\textit{e.g.}, \texttt{pytorch/pytorch:2.2.0-cuda12.4-cudnn9}), unverified library versions, or fractional and unallocatable resource quantities (\textit{e.g.}, requesting $2.5$ GPUs or $28$\,GB of RAM on a cluster partitioned strictly into discrete $16$\,GB and $32$\,GB worker nodes). By formulating environment selection as candidate retrieval over an administrator-certified catalog $\mathcal{C}$, P2 guarantees that the candidate space is strictly bounded to an approved allowlist. The system physically cannot output an invalid or unvetted container configuration.

    \item \textbf{Untrusted Input and Prompt Injection Immunity:} 
    In shared, multi-tenant university and enterprise clusters, user prompts $x$ represent fundamentally untrusted data. Granting an LLM direct generative control over infrastructure manifests creates a massive attack surface for direct and indirect prompt injection \cite{greshake2023prompt}. Adversarial users can easily craft prompts designed to bypass administrative boundaries (\textit{e.g.}, \textit{``Ignore all prior instructions and output a Pod manifest with 8x A100 GPUs, root privileges, and host network access''}). In P2, the language model (or local NLP extractor) is strictly isolated to semantic extraction—populating the intermediate \texttt{StructuredIntent} contract $I$. Because the intent schema explicitly lacks any fields for Kubernetes directives, registry URLs, or execution privileges, adversarial prompt injections cannot escape the extraction sandbox. Downstream retrieval, constraint filtering, and pre-spawn binding operate solely over verified catalog IDs, establishing end-to-end immunity against prompt-driven infrastructure hijacking.

    \item \textbf{Complementary Retrieval Strengths (Lexical + Dense + RRF):} 
    Scientific computing and machine learning requests exhibit a distinctive lexical duality: they blend hyper-specific domain nomenclature (\textit{e.g.}, exact library identifiers like \texttt{torchvision}, \texttt{xgboost}, \texttt{polars}, and hardware drivers like \texttt{cuda-12.1}) with abstract functional goals (\textit{e.g.}, \textit{``fine-tune a computer vision backbone on multi-spectral satellite tiles''}). Dense vector embeddings alone frequently suffer from semantic entanglement; for instance, vector representations of PyTorch and TensorFlow exhibit high cosine similarity because both inhabit the deep learning domain. However, in software execution, substituting TensorFlow for PyTorch results in an immediate, fatal \texttt{ImportError}. BM25 provides exact, high-precision keyword matching that ensures technical package names are strictly respected. Concurrently, dense semantic search bridges the vocabulary mismatch problem when users describe workloads conceptually without naming specific packages. Reciprocal Rank Fusion (RRF) elegantly reconciles these complementary channels based on ordinal rank positions \cite{rrf}, eliminating the need to calibrate unstable linear weights across heterogeneous score distributions ($[0, \infty)$ vs.\ $[-1, 1]$).

    \item \textbf{Hard Constraint Guarantees vs.\ Generative Arithmetic Weakness:} 
    Autoregressive transformers are statistical token predictors that lack intrinsic symbolic verification engines. Recent theoretical and empirical studies demonstrate that transformers struggle with compositionality, multi-step arithmetic reasoning, and strict inequality constraints \cite{dziri2023transformers}. In infrastructure sizing, resource boundaries represent non-negotiable hard inequalities:
    \begin{equation}
    c.\mathrm{mem\_limit} \ge I.\mathrm{min\_ram} \quad \land \quad c.\mathrm{mem\_limit} > I.\mathrm{dataset\_size\_gb}.
    \end{equation}
    Generative models frequently fail to enforce these arithmetic inequalities, recommending undersized profiles due to superficial prompt cues (\textit{e.g.}, selecting a 4\,GB profile for an ``exploratory data analysis'' query that explicitly notes a 10\,GB dataset). As demonstrated in our cluster pod trials (Section~\ref{subsec:e4_cluster_trials}), under-provisioned memory bounds trigger immediate kernel termination (OOMKilled). P2's deterministic constraint filtering evaluates exact Boolean predicates ($H(I, c) = \prod_j h_j(I, c)$), mathematically guaranteeing a 0\% hard constraint violation rate among surviving candidates.

    \item \textbf{Operational Latency and Edge Economics:} 
    Interactive notebook spawning is a latency-critical user interaction. Cloud-based generative LLM invocations introduce severe network latency, queueing delays, and autoregressive token generation overhead, incurring typical response times of $800$ to $3,000$\,ms (averaging $1,508$\,ms in our benchmarks). In contrast, P2's hybrid retrieval and deterministic constraint filtering executes in under $2$\,ms. Combined with the local NLP extraction pipeline ($2.28$\,ms), the complete recommendation cycle finishes in under $5$\,ms—an end-to-end acceleration of more than $350\times$. Furthermore, querying commercial LLM APIs introduces continuous financial expenditures (\$ per thousand tokens), vendor lock-in, and downtime vulnerability during external API outages. Hosting generative LLMs locally on cluster nodes would consume tens of gigabytes of precious GPU memory solely for spawner routing. P2's hybrid architecture requires \$0 in operational API costs and runs entirely on commodity CPU cores, preserving 100\% of high-performance GPU hardware for scientific computation.
\end{enumerate}


\section{Constraint filtering}

After candidate retrieval, each candidate in shortlist $L_f$ undergoes strict constraint evaluation. We treat hard constraints as non-negotiable operational requirements. If a candidate fails a single check, the evaluator prunes it immediately, regardless of how well it scored during retrieval.

Let $h_j(I, c) \in \{0, 1\}$ denote the binary outcome of the $j$-th constraint predicate for candidate $c$ and intent $I$. The overall feasibility predicate $H(I, c)$ is their conjunction:
\[
H(I, c) = \prod_{j=1}^{J} h_j(I, c).
\]
Candidate $c$ is feasible if and only if $H(I, c) = 1$. The feasible set $F$ contains all surviving candidates:
\[
F = \left\{ c \in L_f \mid H(I, c) = 1 \right\}.
\]

Table~\ref{tab:hard_constraints_spec} lists all hard constraints, predicates, and error codes. Figure~\ref{fig:p2_constraints_flow} illustrates the decision tree executed for each candidate.

Hardware accelerator, CPU, and memory requirements are evaluated via binary threshold checks:
\[
h_{\mathrm{GPU}}(I, c) = \mathbb{I}(I.\mathrm{gpu\_requirement} \neq \texttt{required} \lor c.\mathrm{has\_gpu} = \text{true}),
\]
\[
h_{\mathrm{CPU}}(I, c) = \mathbb{I}(c.\mathrm{cpu\_limit} \ge I.\mathrm{min\_cpu}),
\]
\[
h_{\mathrm{RAM}}(I, c) = \mathbb{I}(c.\mathrm{mem\_limit} \ge I.\mathrm{min\_ram} \land c.\mathrm{mem\_limit} > I.\mathrm{dataset\_size\_gb}).
\]
If an intent requests a GPU, CPU-only profiles are rejected. Profile memory limits must also exceed both the requested minimum RAM and the declared dataset size. This check prevents pods from crashing immediately with Out-Of-Memory (OOM) errors.

Software capabilities are verified through set operations against catalog metadata:
\[
h_{\mathrm{caps}}(I, c) = \mathbb{I}(I.\mathrm{req\_feats} \subseteq c.\mathrm{capabilities}) \cdot \mathbb{I}(I.\mathrm{forbid\_feats} \cap c.\mathrm{capabilities} = \emptyset).
\]
We follow a strict zero-assumption rule: if a package or driver is not explicitly listed in the catalog record, we assume it is absent. Dense semantic similarity cannot substitute for verified software declarations.

In P2, an empty feasible set ($F = \emptyset$) is a normal, first-class outcome. If no candidate satisfies all mandatory rules, the system does not guess or quietly relax constraints. Instead, it stops and returns \texttt{no\_feasible\_candidate}. The UI highlights the exact constraint failures (for example, insufficient GPU memory or a missing library), letting the user adjust their prompt or pick a profile manually. This fail-safe behavior turns hidden under-provisioning bugs into clear, actionable notifications.

\section{Multi-criteria candidate ranking}

\subsection{Scoring formulation}

All feasible candidates $c \in F$ are scored across three dimensions: retrieval relevance, user preferences, and resource footprint. The composite score $S(c) \in [0, 1]$ is:
\[
S(c) = w_{\mathrm{ret}} \cdot U(r_f(c)) + w_{\mathrm{pref}} \cdot S_{\mathrm{pref}}(I, c) + w_{\mathrm{res}} \cdot (1.0 - \operatorname{Cost}(c)),
\]
where $U(r_f(c))$ is the linear rank utility from fused retrieval rank $r_f(c)$, $S_{\mathrm{pref}}(I, c) \in [0, 1]$ measures soft preference matching, and $\operatorname{Cost}(c) \in [0, 1]$ is the normalized resource cost. The component weights are:
\[
w_{\mathrm{ret}} = 0.60, \quad w_{\mathrm{pref}} = 0.25, \quad w_{\mathrm{res}} = 0.15,
\]
which sum to $1.00$.

\subsection{Utility and resource cost modeling}

The rank utility function $U(r)$ converts ordinal retrieval positions into linear scores:
\[
U(r) = \max\left(0.0, \, 1.0 - \delta_{\mathrm{rank}} \cdot (r - 1)\right),
\]
with rank decay $\delta_{\mathrm{rank}} = 0.10$. Each drop in retrieval rank reduces the overall score by $w_{\mathrm{ret}} \cdot \delta_{\mathrm{rank}} = 0.06$. This linear formulation makes candidate promotion easy to reason about: strong user preferences alone ($w_{\mathrm{pref}} = 0.25$) can move a candidate up by four ranks ($0.25 / 0.06 \approx 4.17$). When combined with high resource efficiency ($0.25 + 0.15 = 0.40$), an attractive candidate can jump from rank 7 to rank 1.

The cost metric $\operatorname{Cost}(c)$ enforces resource frugality: among viable candidates, P2 prefers the one with the smallest resource envelope, preserving cluster capacity for other workloads \cite{k8sresources,resourcecentral}:
\[
\operatorname{Cost}(c) = \frac{\alpha_{\mathrm{cpu}} \cdot \frac{c.\mathrm{cpu}}{\max \mathrm{CPU}} + \alpha_{\mathrm{ram}} \cdot \frac{c.\mathrm{ram}}{\max \mathrm{RAM}} + \alpha_{\mathrm{gpu}} \cdot \frac{c.\mathrm{gpu}}{\max \mathrm{GPU}}}{\alpha_{\mathrm{cpu}} + \alpha_{\mathrm{ram}} + \alpha_{\mathrm{gpu}}},
\]
where weights are set to $\alpha_{\mathrm{cpu}} = 1.0$, $\alpha_{\mathrm{ram}} = 1.0$, and $\alpha_{\mathrm{gpu}} = 2.0$, reflecting GPU scarcity.

Algorithm~\ref{alg:deterministic_ranking} details candidate scoring and tie-breaking. Feasibility checks are handled directly by $\operatorname{IsFeasible}(I, c)$. If candidates share the same score, P2 resolves ties using a strict four-element tuple: descending score ($-S(c)$), ascending resource cost ($\operatorname{Cost}(c)$), ascending retrieval rank ($r$), and alphanumeric candidate ID.

\begin{algorithm}[ht]{Deterministic candidate evaluation, multi-criteria scoring, and tie-breaking}
\label{alg:deterministic_ranking}
\begin{algorithmic}[1]
\Require Fused candidate shortlist $L_f$, structured intent $I$, weights $(w_{\mathrm{ret}}, w_{\mathrm{pref}}, w_{\mathrm{res}})$, rank decay $\delta_{\mathrm{rank}}$
\Ensure Recommended candidate identifier $c^*$ (or $\emptyset$ if no candidate is feasible)
\State $\mathcal{F} \gets \emptyset$
\For{each candidate $c \in L_f$}
    \If{$\neg \operatorname{IsFeasible}(I, c)$}
        \State \textbf{continue} \Comment{Prune candidate violating hard constraints}
    \EndIf
    \State $r \gets \operatorname{rank}(c, L_f)$
    \State $U(r) \gets \max\big(0.0, \, 1.0 - \delta_{\mathrm{rank}} \cdot (r - 1)\big)$
    \State $S(c) \gets w_{\mathrm{ret}} \cdot U(r) + w_{\mathrm{pref}} \cdot S_{\mathrm{pref}}(I, c) + w_{\mathrm{res}} \cdot (1.0 - \operatorname{Cost}(c))$
    \State $\mathcal{F} \gets \mathcal{F} \cup \{\langle c, S(c), \operatorname{Cost}(c), r \rangle\}$
\EndFor
\If{$\mathcal{F} = \emptyset$}
    \State \Return $\emptyset$ \Comment{Trigger \texttt{no\_feasible\_candidate} outcome}
\EndIf
\State $c^* \gets \operatorname{ArgMin}_{c \in \mathcal{F}} \big(-S(c), \, \operatorname{Cost}(c), \, r, \, c\big)$ \Comment{Deterministic 4-key total order}
\State \Return $c^*$
\end{algorithmic}
\end{algorithm}

\section{JupyterHub integration and runtime enforcement}

\subsection{Policy validation and candidate resolution}
\label{subsec:policy_validation}

The candidate ID $c^*$ selected by the ranker cannot trigger a container spawn on its own. Before showing any recommendation to the user, P2 passes $c^*$ through the \texttt{PolicyValidator} to confirm catalog integrity.

The validator checks six explicit rules:
\begin{enumerate}
    \item The selected profile ID exists in the active profile allowlist.
    \item The container image ID exists in the active image allowlist.
    \item The image reference matches the catalog's digest-pinned SHA-256 hash per the OCI Image Specification \cite{oci}.
    \item The running policy version matches the cluster configuration.
    \item The catalog checksum matches the deployed provenance record.
    \item The recommendation data payload conforms to the deployment schema.
\end{enumerate}

These checks prevent unvetted images or misconfigured resource limits from reaching Kubernetes, even if the upstream ranking service behaves unexpectedly.

\subsection{Two-phase preview and confirmation}
\label{subsec:preview_workflow}

P2 adopts a two-phase preview and confirmation lifecycle to keep human users in control (Figure~\ref{fig:p2_preview_lifecycle}), adhering to established principles of human-in-the-loop automation and declarative intent fulfillment \cite{parasuraman,rfc9315}. 

\begin{figure}[ht]{Two-phase preview, user confirmation, and pre-spawn binding lifecycle}
\centering
\includegraphics[width=0.98\textwidth]{figures/figure_3_3_preview_spawn_lifecycle.pdf}
\label{fig:p2_preview_lifecycle}
\end{figure}

The lifecycle proceeds as follows:
\begin{itemize}
    \item \textbf{Phase 1: Preview Generation.} The user submits a workload description. The backend resolves the best candidate, verifies policy checks, and saves a preview record. This record contains a fresh UUIDv4 token, the user's identity, a timestamp, a 30-minute expiration TTL (1,800 seconds), and the target profile and image configuration. The JupyterHub UI displays the recommendation, its resource limits, and an explanation.
    \item \textbf{Phase 2: Confirmation and Binding.} The user reviews the recommendation. If they edit the prompt, P2 invalidates the token and regenerates the preview. Once the user clicks confirm (or selects an alternative profile manually), the client submits the preview token with the spawn request. The server consumes the token atomically and launches the pod.
\end{itemize}

\subsection{Pre-spawn binding and execution}
\label{subsec:prespawn_binding}

A core property of our JupyterHub integration is zero recomputation during pod launch. In typical KubeSpawner setups, users submit spawn requests through web forms. P2 intercepts this flow with a synchronous \texttt{pre\_spawn\_hook} provided by KubeSpawner \cite{kspawner}.

Algorithm~\ref{alg:prespawn_enforcement} describes the hook's validation and binding steps.

\begin{algorithm}[ht]{JupyterHub pre-spawn policy validation and deterministic resource binding}
\label{alg:prespawn_enforcement}
\begin{algorithmic}[1]
\Require Spawner instance $spawner$, catalogs $(\mathcal{P}, \mathcal{I})$, preview store $\mathcal{S}_{\mathrm{previews}}$
\Ensure Configures $spawner$ parameters authoritatively or aborts spawn
\State $\langle token, user, action \rangle \gets \operatorname{ExtractSubmissionOptions}(spawner)$
\State $item \gets \operatorname{ValidatePreview}(\mathcal{S}_{\mathrm{previews}}, token, user)$ \Comment{Validates token existence, user binding, and TTL}
\If{$action \notin \{\text{"accept"}, \text{"override"}\}$}
    \State \textbf{abort}(\texttt{"Invalid recommendation decision action"})
\EndIf
\State $\langle profile, image \rangle \gets \operatorname{ResolveAllowlistedEntities}(item, \mathcal{P}, \mathcal{I})$
\State $\operatorname{ConsumeToken}(\mathcal{S}_{\mathrm{previews}}, token)$ \Comment{Single-use consumption prevents replay}
\State $\operatorname{ApplyResourceConfiguration}(spawner, profile)$ \Comment{Inject CPU/RAM limits and guarantees}
\State $spawner.\mathrm{image} \gets image.\mathrm{digest\_reference}$ \Comment{Immutable digest reference}
\State $\operatorname{AttachAuditAnnotations}(spawner, item)$
\end{algorithmic}
\end{algorithm}

When JupyterHub initiates pod creation, the pre-spawn hook executes before the Pod manifest reaches the Kubernetes API. The hook extracts the preview token, checks its user ID and TTL, confirms allowlist membership, and writes the CPU/memory limits and digest-pinned image directly into the spawner object. It also attaches structured audit annotations (event ID, profile, and image) to the pod metadata.

Crucially, the pre-spawn hook performs no NLP parsing, vector inference, or candidate ranking. It only applies the previously accepted configuration. This zero-recomputation design avoids Time-of-Check to Time-of-Use (TOCTOU) discrepancies: the pod that starts in the cluster is guaranteed to match what the user approved during preview. In addition, removing inference from the critical launch path keeps pod startup fast, predictable, and resilient against external model outages.

\subsection{Policy-bounded dynamic resource overlay}
\label{subsec:dynamic_resource_overlay}

While P2 defaults to mapping user intent onto discrete, administrator-curated profiles from catalog $\mathcal{P}$ (\textbf{Catalog Mode}), the architecture also provides an opt-in extension for fine-grained resource tailoring (\textbf{Dynamic Mode}). 

In standard Catalog Mode, P2 assigns one of the fixed, pre-configured profile tiers (such as \texttt{Small}, \texttt{Medium}, or \texttt{Large}). While this discrete mapping guarantees high operational predictability and strict adherence to administrator-certified resource templates, it can lead to memory over-allocation when workload requirements fall between coarse profile tiers.

To address cluster multi-tenancy and optimize physical memory footprint, Dynamic Mode introduces a policy-bounded resource generation overlay layered directly onto the resolved recommendation. Rather than binding static profile quantities, the dynamic engine estimates continuous CPU and memory bounds from the validated intent contract $I$ (specifically exploiting extracted task categories, estimated dataset scale $I.\mathrm{dataset\_size\_gb}$, and explicit UI resource hints $H_{\mathrm{user}}$). To guarantee infrastructure stability and prevent arbitrary resource injections, the dynamic generator enforces three administrative safeguards:
\begin{enumerate}
    \item \textbf{Stepped Quantity Bounds:} All dynamically generated CPU millicores and memory megabytes must fall within administrator-configured minimums and maximums, aligned upward to discrete step intervals ($[\mathrm{min}, \mathrm{max}]$ with step $\Delta$) defined in the resource policy.
    \item \textbf{Cluster Quota Caps and Ratios:} Generated quantities must satisfy strict limit-to-request ratios and cannot exceed the active Kubernetes namespace quota headroom.
    \item \textbf{Cryptographic Policy Provenance:} Every dynamic allocation binds a cryptographic SHA-256 digest of the governing policy file into the preview record, ensuring that policy alterations immediately invalidate stale or unverified spawn requests.
\end{enumerate}
This dual-mode design establishes a flexible operational spectrum: cluster administrators can maintain Catalog Mode for guaranteed workload containment and zero out-of-memory risk, or activate Dynamic Mode to maximize cluster packing density and eliminate idle capacity stranding.
