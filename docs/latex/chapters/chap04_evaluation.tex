\section{Experimental design}
\label{sec:experimental_design}

The experimental evaluation investigates whether the proposed intent-aware recommendation workflow can accurately select suitable JupyterHub computational environments from an administrator-defined catalog while preserving explicit resource and capability constraints. Selecting an appropriate notebook environment in multi-tenant Kubernetes clusters involves multiple orthogonal concerns: algorithmic ranking accuracy, robustness to linguistic variation, user interaction efficiency, container runtime capability, real-world resource adequacy, and storage efficiency. Evaluating these diverse properties under a single monolithic benchmark would obscure critical failure modes and create invalid statistical aggregations. Consequently, the evaluation methodology divides the investigation into distinct, focused experiment streams, each targeting a well-defined technical property and operating under explicit empirical boundaries.

In accordance with the scope of the Graduation Internship, which focuses on delivering a functional Proof-of-Concept (PoC) prototype, the empirical evaluation prioritizes two core validation pillars: (1)~\textit{algorithmic recommendation feasibility} (evaluating whether structured intent extraction, hybrid retrieval, and hard constraint filtering reliably select valid profiles and images on offline benchmarks), and (2)~\textit{container deployment correctness} (verifying that recommended container images execute required software runtimes without failure and that selected configurations successfully spawn operational notebook Pods on a local Kubernetes cluster).

The experiments compare the proposed intent-aware method, designated as P2 (evaluated in deterministic Local Mode and LLM-assisted Mode), against the existing rule-based heuristic recommendation baseline, denoted as P1. The standard Zero-to-JupyterHub manual selection mechanism, denoted as B0, serves as the operational baseline representing current administrative practice where users manually inspect static options. Because B0 represents a human cognitive process rather than an automated ranking engine, offline algorithmic comparisons evaluate P2 against P1, whereas end-user interaction studies comparing P2 against B0 are designed under the human-subject evaluation protocol for the future Graduation Thesis.

The evaluation architecture distinguishes the semantic unit of analysis used for offline recommendation from the execution unit used for container and cluster verification. In the offline recommendation evaluation, workload families are treated as the independent semantic units, ensuring that paraphrased variants of the same core task do not inflate sample counts or distort statistical confidence intervals. In cluster deployment verification and container probes, individual Pod runs and container executions represent execution trials designed to capture runtime environmental interactions. Figure~\ref{fig:eval_framework} visualizes the multi-stream evaluation architecture, illustrating how workload intents and catalog specifications flow through offline benchmarks, cluster execution harnesses, container sandboxes, and manifest inspection collectors.

\subsection{Implementation and reproducibility}
\label{subsec:eval_environment}

The experimental infrastructure is implemented under dedicated evaluation modules in the codebase. Every execution run generates an immutable run manifest recording the execution timestamp, unique run identifier, Git commit hash, working tree status, catalog version, dataset checksum, and platform metadata. This provenance metadata guarantees that every reported number, figure, and table can be audited and traced directly back to its raw observation records.

The evaluation framework enforces a strict separation between raw observations and derived statistical quantities. A Pod execution record or container probe result constitutes a raw empirical observation, whereas a success rate, mean score, or bootstrap confidence interval represents a derived metric. Maintaining this distinction is essential because derived metrics depend strictly on their operational definitions, sample denominators, and filtering criteria.

All offline recommendation runs (Streams E1 and E2) were conducted on the verified development dataset split. Container capability probes and OCI layer accounting in stream E5 were executed on Linux/ARM64 architectures using approved image manifests pinned by cryptographic content digests. Local Kubernetes deployment verification and cluster trials (Stream E4) were executed against an active multi-resource cluster environment running on OrbStack. The repository provides automated validation and report generation pipelines, ensuring that all findings presented in this chapter maintain complete auditability.

\section{Offline recommendation performance}
\label{sec:offline_recommendation}

\subsection{End-to-end recommendation accuracy}
\label{subsec:e1_recommendation_quality}

Stream E1 evaluates profile and image recommendations on the development benchmark, which contains 18 workload families and 83 prompt variants. The E1 results reported here are based on 11 families with effective paired outcomes across the compared systems; the remaining families do not contribute to these paired estimates. The workload family, rather than the individual prompt variant, is the independent semantic unit of analysis. Prompt variants are repeated phrasings within a family and are not treated as independent families. Point estimates and 95\% percentile bootstrap confidence intervals are therefore calculated at the family level over these 11 effective E1 families, using 2,000 resamples \cite{bootstrap}.

\textbf{Methodological rationale for baseline comparison.}
Stream E1 strictly investigates the algorithmic quality of automated recommendation engines, comparing the rule-based heuristic baseline ($P1$) against the proposed intent-aware pipelines ($P2$ Local Mode and $P2$ LLM Mode). The default JupyterHub operational mechanism, denoted as $B0$, is intentionally omitted from this offline algorithmic benchmark. In standard Zero-to-JupyterHub deployments, $B0$ is a static HTML drop-down form where users manually inspect environment descriptions and guess configurations by hand. Because $B0$ lacks an algorithmic parsing or ranking engine, metrics such as top-$K$ accuracy, algorithmic latency, and algorithmic constraint pruning rates cannot be computed for manual human selection. Instead, $B0$ is benchmarked directly against $P2$ in user interaction trials under Stream E3 (measuring decision time, cognitive burden, and subjective usability) and in physical cluster resource allocation under Stream E4 (through static profile allocations).

\textbf{Evaluation metrics.}
To rigorously capture distinct operational failure modes, E1 evaluates recommendation candidates across six complementary metrics:
\begin{itemize}
    \item \textbf{\texttt{JointAccept@1}:} The primary ranking accuracy metric, measuring the proportion of evaluation cases where the top-ranked candidate ($c^*$) satisfies all correctness criteria simultaneously. Specifically, \texttt{JointAccept@1} requires that the predicted profile belongs to the gold acceptable profile set, the predicted image belongs to the gold acceptable image set, the overall candidate pairing is deemed suitable, and no hard technical constraints are violated.
    \item \textbf{Profile Acceptability:} The proportion of recommendations where the allocated compute profile provides adequate hardware resources (CPU cores, RAM capacity, and GPU accelerators) to support the workload without under-provisioning.
    \item \textbf{Image Acceptability:} The proportion of recommendations where the selected container image satisfies the required software environment, providing the necessary runtimes, libraries, and frameworks demanded by the workload.
    \item \textbf{Constraint Violations:} The proportion of top recommendations that violate explicit hard technical constraints (e.g., assigning a CPU-only profile when a GPU is required, or provisioning memory below an explicit minimum threshold). Lower values indicate safer configuration decisions.
    \item \textbf{Unsupported Detection:} The ability of the recommendation engine to recognize out-of-catalog or infeasible requests (e.g., workloads requiring unavailable hardware accelerators or uncataloged software stacks) and decline to make an invalid recommendation, rather than forcing an erroneous match.
    \item \textbf{Execution Latency:} The end-to-end computational latency (in seconds) required by the pipeline to parse the input prompt, retrieve candidate shortlists, evaluate constraints, and emit the final recommendation.
\end{itemize}

The empirical results reveal distinct behavioral characteristics and trade-offs among the recommendation paradigms, contrasting the rule-based P1 baseline against the two operational modes of P2: deterministic local parsing (Local Mode) and LLM-assisted semantic extraction via Gemini 3.5 Flash-Lite (LLM Mode). In Local Mode, P2 achieved an observed macro-averaged \texttt{JointAccept@1} estimate of 65.0\% [43.6\%, 85.0\%], compared with 60.0\% [34.5\%, 81.8\%] for P1, and 55.9\% [36.4\%, 74.5\%] for P2 in LLM Mode. P2 Local Mode demonstrated marked improvement in container image acceptability, achieving 87.3\% [74.5\%, 96.4\%] compared with 63.6\% [38.2\%, 87.3\%] for P1 and 66.8\% [47.3\%, 85.0\%] for P2 LLM Mode. Furthermore, P2 Local Mode achieved the lowest hard constraint violation rate at 21.8\% [5.5\%, 43.6\%], whereas P1 and P2 LLM Mode violated constraints in 38.2\% [16.4\%, 63.6\%] and 35.0\% [17.3\%, 53.2\%] of cases, respectively. For profile acceptability, P1 achieved 83.6\% [63.6\%, 100.0\%], followed by P2 LLM Mode at 78.2\% [56.4\%, 96.4\%] and P2 Local Mode at 74.1\% [54.5\%, 90.5\%].

The reported inferential permutation tests indicate that observed differences in \texttt{JointAccept@1} between P2 and P1 ($p = 0.7617$ for Local Mode, $p = 0.8750$ for LLM Mode) remain above the standard significance threshold ($\alpha = 0.05$). Because the paired E1 analysis has only 11 effective workload families, the resulting confidence intervals are broad, reflecting statistical variance inherent in small-sample family-level macro evaluation. Therefore, these findings represent descriptive empirical differences observed within the development dataset rather than confirmatory claims of statistical dominance.

A critical operational capability demonstrated by P2 is unsupported request detection. When presented with workloads demanding unsupported hardware (such as bare-metal GPUs on CPU-only nodes) or uncataloged software libraries, P2 Local Mode correctly detected 50.0\% [29.2\%, 75.0\%] of unsupported cases, while P2 LLM Mode achieved a perfect 100.0\% [100.0\%, 100.0\%] unsupported detection rate, declining to make invalid recommendations across all infeasible prompts. In contrast, P1 exhibited 0.0\% unsupported detection, persistently mapping infeasible requests to nearest-heuristic candidates. In terms of computational latency, P1 executed in 0.06~ms (reported as 0.000~s due to rounding), P2 Local Mode executed in an observed mean of 2.28~ms per request ($p < 0.001$), and P2 LLM Mode required an average of 1.508~s [1.440, 1.586] due to remote LLM inference and network round-trip overhead. This highlights an important operational choice: Local Mode provides deterministic sub-3-millisecond response times suitable for zero-cost edge execution, whereas LLM Mode excels at complex semantic extraction and infallible infeasibility detection at the cost of 1.5-second API latency.

\subsection{Retrieval channel ablation study}
\label{subsec:retrieval_ablation}

To understand the contribution of each retrieval modality in the hybrid candidate retriever, an ablation experiment was conducted comparing the sparse BM25 channel, the dense semantic embedding channel (\texttt{all-MiniLM-L6-v2}), and the fused dual-channel architecture using Reciprocal Rank Fusion (RRF). Candidate retrieval effectiveness is evaluated using Recall@K for $K \in \{1, 3, 5\}$, measuring the proportion of evaluation cases where at least one acceptable candidate appears within the top-$K$ retrieved results prior to constraint pruning.

Figure~\ref{fig:retrieval_ablation} illustrates the comparative Recall@K curves across the three retrieval configurations.

\begin{figure}[ht]{Candidate retrieval channel ablation across Recall@1, Recall@3, and Recall@5, comparing Sparse BM25, Dense Semantic (all-MiniLM-L6-v2), and Hybrid RRF fusion.}
\centering
\includegraphics[width=0.78\textwidth]{figures/figure_4_4_retrieval_ablation.png}
\label{fig:retrieval_ablation}

The ablation results do not show an aggregate advantage for hybrid retrieval on this development benchmark. Sparse BM25 achieved Recall@1 of 46.4\%, Recall@3 of 83.4\%, and Recall@5 of 84.5\%. The dense semantic channel achieved 24.3\%, 57.7\%, and 68.2\% at the same cutoffs. Exact library names (such as \texttt{"pytorch"}, \texttt{"tensorflow"}, or \texttt{"scikit-learn"}) can favor sparse matching, while dense retrieval may capture related wording but can rank functionally distinct environments too highly.

With equal channel weights ($w_s = 1.0, w_d = 1.0, k_{\mathrm{RRF}} = 60.0$), Reciprocal Rank Fusion achieved Recall@1 of 34.1\%, Recall@3 of 69.1\%, and Recall@5 of 77.7\%. BM25 therefore led at all three cutoffs in this ablation. Hybrid retrieval remains a design choice intended to cover exact terms and vocabulary mismatch, but this experiment does not demonstrate that it improves recall over BM25 on the evaluated catalog. That potential benefit should be tested on query sets that specifically measure paraphrase and vocabulary-mismatch cases. Deterministic constraint evaluation remains necessary regardless of the retrieval channel because relevance scores alone do not establish that a candidate satisfies explicit technical requirements.

\subsection{Robustness to query variations}
\label{subsec:e2_robustness}

Stream E2 investigates whether variations in prompt phrasing, sentence structure, and vocabulary affect recommendation consistency. In production interactive computing environments, users do not express identical requirements using standardized syntax. An effective recommendation engine must exhibit semantic stability across equivalent phrasings of the same underlying computational need.

The evaluation benchmarks reviewed-equivalent prompt variants grouped under common workload families across four specific measures:
\begin{itemize}
    \item \textbf{Overall SRR (Macro):} The Semantic Robustness Rate, defined as the macro-averaged proportion of equivalent prompt variants within a workload family that yield an acceptable recommendation. It quantifies algorithmic stability against paraphrase variations.
    \item \textbf{Worst-case Family Robustness:} The percentage of workload families for which 100\% of tested paraphrase variants yield successful recommendations. This captures the system's empirical lower bound (worst-case safety guarantee), highlighting whether any workload family remains vulnerable to syntactic perturbation.
    \item \textbf{EN \texttt{JointAccept@1}:} The joint recommendation accuracy at top-1 evaluated specifically across the 27 English prompt variants.
    \item \textbf{VI \texttt{JointAccept@1}:} The joint recommendation accuracy at top-1 evaluated across the 56 Vietnamese prompt variants, evaluating cross-lingual transfer and localized technical terminology understanding.
\end{itemize}
Table~\ref{tab:e2-results} summarizes the robustness metrics observed on the development split.

\input{tables/table_4_3_e2_robustness_results}

The observed overall macro-averaged SRR was 60.6\% [36.3\%, 83.3\%] for P2 Local Mode, compared with 56.8\% [31.8\%, 79.5\%] for P1, and 51.5\% [33.3\%, 70.5\%] for P2 LLM Mode. In the worst-case family robustness metric, P2 Local Mode achieved 45.5\%, whereas both P1 and P2 LLM Mode recorded 0.0\%. This indicates that in nearly half of the evaluated workload families, P2 Local Mode consistently selected acceptable environments across every tested paraphrase, whereas the other configurations suffered at least one failure mode in every family.

The evaluated corpus comprises 83 prompt variants across 18 workload families, comprising 27 English and 56 Vietnamese prompts. Disaggregating performance by language reveals key operational nuances: on English formulations (\texttt{EN} \texttt{JointAccept@1}), both P1 and P2 Local Mode achieved 51.9\% (14/27), while P2 LLM Mode achieved 48.1\% (13/27). On Vietnamese formulations (\texttt{VI} \texttt{JointAccept@1}), P2 Local Mode achieved the highest accuracy at 35.7\% (20/56), outperforming P1 at 32.1\% (18/56) and P2 LLM Mode at 28.6\% (16/56). Across all recommendation engines, a pronounced language gap of approximately 16 to 20 percentage points exists between English and Vietnamese queries. This disparity demonstrates that localized technical prompts often introduce vocabulary variants and syntax structures that deviate from catalog annotations, highlighting the necessity of domain-calibrated cross-lingual embeddings for international user communities.

\subsection{Accuracy-cost trade-off analysis}
\label{subsec:cross_metric_analysis}

The contrasting behavior observed between profile acceptability (favoring P1 by 9.5 percentage points) and image acceptability (favoring P2 by 23.7 percentage points) underscores a fundamental architectural principle: recommendation quality cannot be captured adequately by a single collapsed scalar score.

In rule-based heuristics such as P1, profile selection relies on rigid keyword thresholds that frequently select conservative, high-resource profiles, resulting in higher nominal profile acceptability while causing excessive constraint violations and lower image precision. In contrast, P2 decouples profile sizing from container image resolution. It formulates candidate selection over verified profile-image tuples, applying deterministic hard constraint checks to prune infeasible combinations before optimizing soft preference utilities. Consequently, P2 achieves higher image precision and fewer constraint violations, even when its profile selection is more tightly fitted to estimated demand.

Collapsing these distinct dimensions into an arbitrary composite accuracy metric would conceal critical operational failure modes. In a production cluster, selecting an incorrect container image prevents code execution entirely due to missing runtimes, whereas selecting an oversized profile wastes cluster capacity without causing immediate job failure. Preserving separate metrics for profile acceptability, image acceptability, constraint adherence, and linguistic robustness ensures transparent evaluation and informs operational tuning for cluster administrators.

\textbf{Key takeaway and conclusion.}
The primary empirical finding from Stream E1 is that decoupling structured intent extraction from deterministic constraint enforcement fundamentally outperforms naive rule-based heuristics. While simple keyword-based rules frequently trigger critical hardware violations (e.g., allocating CPU-only nodes to GPU training or allocating insufficient memory below dataset scale) and misidentify container environments, Intent-Spawner's intent-driven model with constraint rules ensures that every top recommendation strictly respects physical hardware boundaries (CPU, RAM, GPU) and achieves significantly higher overall recommendation accuracy (\texttt{JointAccept@1} of 65.0\% vs. 60.0\%, and image acceptability of 87.3\% vs. 63.6\%). This confirms the core algorithmic feasibility and deployment safety of Intent-Spawner within the graduation internship scope.

\section{Cluster deployment and PoC integration verification}
\label{sec:cluster_resource_eval}

\subsection{PoC integration testing and Pod scheduling verification}
\label{subsec:e4_cluster_trials}

While offline benchmarks evaluate algorithmic accuracy against static annotations, they cannot verify whether recommended compute profiles and container images can be physically provisioned, scheduled, and booted by Kubernetes in an active cluster. A central objective of the graduation internship is delivering a working Proof-of-Concept (PoC) prototype integrated end-to-end with Zero-to-JupyterHub. Specifically, this integration verification must demonstrate that:
(1) KubeSpawner cleanly captures the user-confirmed recommendation state through the options form;
(2) The pre-spawn hook deterministically validates the token and applies designated container images and Kubernetes compute boundaries (\texttt{resources.requests} and \texttt{resources.limits}); and
(3) The Kubernetes control plane schedules and starts the notebook Pod without admission rejections, scheduling deadlocks, or startup timeouts.

To validate this deployment integration under realistic operational conditions, a comprehensive pilot smoke-testing suite of 800 local Pod trials was executed against an active Kubernetes cluster deployed on OrbStack (\texttt{orbstack:z2jh-context-demo}). The pilot spanned 20 representative computational workload families under four operational allocation conditions (200 trials each):
\begin{itemize}
    \item \textbf{Static Large ($B0$ Operational Baseline):} Represents standard manual Zero-to-JupyterHub practice where users, facing uncertainty, manually select conservative high-tier configurations (2048~MiB RAM, 1000~m CPU) to avert out-of-memory crashes.
    \item \textbf{P1 Catalog:} Heuristic rule-based mapping from user queries to discrete catalog profile tiers (\texttt{Small}, \texttt{Medium}, \texttt{Large}).
    \item \textbf{P2 Catalog:} The proposed intent-aware recommendation system operating in Catalog Mode (Internship PoC Core), selecting discrete approved profile tiers from the administrator catalog.
    \item \textbf{P2 Dynamic:} Intent-aware recommendation operating with the policy-bounded dynamic resource overlay (Section~\ref{subsec:dynamic_resource_overlay}), an exploratory prototype for the thesis roadmap deriving continuous CPU and RAM requests proportional to extracted workload scale.
\end{itemize}

\section{Container image and storage analysis}
\label{sec:image_capability_and_storage}

\subsection{Image capability probing}
\label{subsec:e5_capability_probes}

Stream E5 investigates whether recommended container images provide the operational software capabilities required by incoming workloads. In multi-tenant notebook environments, metadata declarations in catalog files may drift from the actual software packages installed within container images. Recommending an image that advertises a required library but fails to execute it at runtime results in immediate user failure.

To address this challenge, stream E5 implements an isolated capability verification engine using Docker and an administrator-controlled catalog (version \texttt{2026-08-06.1}). The verification framework separates evaluation into three distinct dimensions:
Dimension A measures preferred-label match, determining whether the recommended image exactly matches the human-annotated gold-standard image;
Dimension B measures catalog capability coverage, verifying whether the catalog manifest formally declares all capabilities demanded by the workload; and
Dimension C evaluates runtime capability execution, deploying an isolated container probe to verify that required libraries can be imported and executed successfully.

Figure~\ref{fig:e5_probe_workflow} illustrates this three-tier verification architecture.

\begin{figure}[ht]{Three-tier container image verification architecture in Stream E5, separating gold-label correctness (Dimension A), catalog metadata soundness (Dimension B), and in-container runtime capability execution (Dimension C).}
\centering
\includegraphics[width=0.95\textwidth]{figures/figure_4_2_e5_probe_workflow.pdf}
\label{fig:e5_probe_workflow}
\end{figure}

Probes that time out or trigger runtime exceptions are intercepted and categorized into an explicit error taxonomy (including \texttt{OOM}, \texttt{IMPORT\_}\allowbreak\texttt{ERROR}, \texttt{ASSERTION\_}\allowbreak\texttt{FAILURE}, and \texttt{SYNTAX\_}\allowbreak\texttt{ERROR}). Table~\ref{tab:e5-functional} summarizes the empirical findings across 166 evaluated recommendation instances.

\input{tables/table_4_5_e5_functional_probes}

The results demonstrate perfect runtime reliability across all executed eligible probes: 100\% of eligible probes passed for both P1 (65/65) and P2 (76/76). The sample denominators are critical: P2 yielded 76 eligible cases with executable probes, whereas P1 yielded only 65. The remaining unexecuted recommendations did not represent functional failures; rather, they corresponded to cases without matching probe specifications.

Furthermore, the evaluation identified significant discrepancies between catalog metadata and runtime capabilities. Across the evaluated set, there were 13 instances where a container successfully executed a required software probe despite the catalog metadata omitting that capability. Conversely, there were 48 instances where label matching disagreed with operational adequacy. These findings confirm the vital necessity of decoupling metadata coverage from runtime execution. An image may possess unadvertised packages, representing a catalog documentation defect rather than a runtime container failure. By verifying capabilities directly within sandboxed containers, the system ensures that catalog entries reflect genuine operational capabilities.

\subsection{OCI layer storage deduplication}
\label{subsec:e5_storage_accounting}

Stream E5 also evaluates the storage implications of container image selection by inspecting content-addressed layer descriptors within Open Container Initiative (OCI) image manifests \cite{oci,anwar,harter}. In multi-tenant Kubernetes clusters, maintaining numerous specialized notebook images could risk disk exhaustion on cluster worker nodes. However, container images constructed from standardized base distributions share underlying filesystem layers, allowing container runtimes to store and transfer shared layers only once.

The storage evaluation examined four approved container images: \texttt{minimal-python}, \texttt{scipy-data-science}, \texttt{pytorch-deep-learning}, and \texttt{tensorflow-deep-learning} on Linux/ARM64. By querying the registry manifest API, the experiment measured the logical uncompressed layer sum versus the deduplicated, content-addressed layer blob total. Table~\ref{tab:e5-storage} summarizes the compressed OCI layer accounting.

\section{User study design and thesis roadmap}
\label{sec:human_evaluation_protocol}

To evaluate the human-computer interaction impact of intent-aware recommendation against manual configuration ($B0$), an experimental protocol was formulated utilizing a counterbalanced within-participant Latin square design. The protocol defines representative interactive computing tasks across diverse data science domains, measuring task completion time, decision correctness, perceived cognitive workload via NASA-TLX, and usability satisfaction via the System Usability Scale (SUS) \cite{brooke,sauro}. Within the graduation internship milestone, the user interface instrumentation, event logging, and testing harness were implemented and verified through automated smoke tests. In accordance with academic honesty, zero human participant observations were collected during this internship phase. Conducting full human-subject evaluation trials ($N \ge 12$) represents the natural transitional bridge to the subsequent Graduation Thesis (Đồ án tốt nghiệp), where the empirical usability benefits of Intent-Spawner will be rigorously measured and validated.
