\section{Experimental design}
\label{sec:experimental_design}

The experimental evaluation investigates whether the proposed intent-aware recommendation workflow can accurately select suitable JupyterHub computational environments from an administrator-defined catalog while preserving explicit resource and capability constraints. Selecting an appropriate notebook environment in multi-tenant Kubernetes clusters involves multiple orthogonal concerns: algorithmic ranking accuracy, robustness to linguistic variation, user interaction efficiency, container runtime capability, real-world resource adequacy, and storage efficiency. Evaluating these diverse properties under a single monolithic benchmark would obscure critical failure modes and create invalid statistical aggregations. Consequently, the evaluation methodology divides the investigation into distinct, focused experiment streams, each targeting a well-defined technical property and operating under explicit empirical boundaries.

The experiments compare the proposed intent-aware method, designated as P2, against the existing rule-based heuristic recommendation method, denoted as P1. In the user interaction evaluation, a manual environment selection baseline, denoted as B0, is established to reflect standard operational practice in JupyterHub where users manually navigate available profile options. Because B0 represents a human selection process rather than an algorithmic ranking system, it does not generate automated candidate rankings and is evaluated exclusively through human-subject task outcomes rather than ranking metrics.

The evaluation architecture distinguishes the semantic unit of analysis used for offline recommendation from the execution unit used for cluster and container experiments. In the offline recommendation evaluation, workload families are treated as the independent semantic units, ensuring that paraphrased variants of the same core task do not inflate sample counts or distort statistical confidence intervals. In cluster and container experiments, individual Pod runs and container executions represent execution trials designed to capture runtime variability and environmental interactions. Figure~\ref{fig:eval_framework} visualizes the multi-stream evaluation architecture, illustrating how workload intents and catalog specifications flow through offline benchmarks, cluster execution harnesses, container sandboxes, and manifest inspection collectors.

\subsection{Evaluation environment and reproducibility}
\label{subsec:eval_environment}

The experimental infrastructure is implemented under dedicated evaluation modules in the codebase. Every execution run generates an immutable run manifest recording the execution timestamp, unique run identifier, Git commit hash, working tree status, catalog version, dataset checksum, and platform metadata. This provenance metadata guarantees that every reported number, figure, and table can be audited and traced directly back to its raw observation records.

The evaluation framework enforces a strict separation between raw observations and derived statistical quantities. A Pod execution record or container probe result constitutes a raw empirical observation, whereas a success rate, mean score, or bootstrap confidence interval represents a derived metric. Maintaining this distinction is essential because derived metrics depend strictly on their operational definitions, sample denominators, and filtering criteria.

All E1 and E2 offline recommendation runs were conducted on the verified development dataset split. Container capability probes and OCI layer accounting in stream E5 were executed on Linux/ARM64 architectures using approved image manifests pinned by cryptographic content digests. Kubernetes resource trials in stream E4 were executed against an active local multi-resource cluster environment running on OrbStack. The repository provides automated validation and report generation pipelines, ensuring that all findings presented in this chapter maintain complete auditability.

\section{Offline recommendation and robustness evaluation}
\label{sec:offline_recommendation}

\subsection{Stream E1}
\label{subsec:e1_recommendation_quality}

Stream E1 evaluates the quality of profile and container image recommendations across 18 independent workload families comprising 83 evaluated prompt variants. A central principle of this evaluation is treating the workload family, rather than the individual prompt variant, as the independent semantic unit of analysis. Workload families represent distinct computational tasks (such as distributed deep learning training, tabular classification, or lightweight data transformation), whereas prompt variants represent syntactic and lexical reformulations of those tasks. Pooling all 83 prompt variants as independent statistical observations would artificially inflate statistical power and misrepresent sample independence. Consequently, all reported point estimates represent macro-averages calculated across the 18 workload families, accompanied by 95\% percentile bootstrap confidence intervals derived from 2,000 resamples.

The primary evaluation metric is \texttt{JointAccept@1}, which represents the proportion of evaluation cases where the top-ranked candidate satisfies all correctness criteria simultaneously. Specifically, \texttt{JointAccept@1} requires that the predicted profile belongs to the acceptable profile set, the predicted image belongs to the acceptable image set, the overall candidate pairing is deemed suitable, and no hard technical constraints (such as GPU requirements, CPU minimums, or memory capacities) are violated. In addition to \texttt{JointAccept@1}, the evaluation measures profile acceptability, image acceptability, hard constraint violation rate, unsupported request detection, and end-to-end execution latency. Table~\ref{tab:e1-results} presents the observed empirical estimates for P1 and P2 alongside paired bootstrap permutation test $p$-values.

The empirical results reveal distinct behavioral characteristics and trade-offs between the two recommendation paradigms. The proposed P2 method achieved an observed \texttt{JointAccept@1} estimate of 65.0\% [43.6\%, 85.0\%], compared with 60.0\% [34.5\%, 81.8\%] for the rule-based P1 method. P2 demonstrated substantial improvement in container image acceptability, achieving 87.3\% [74.5\%, 96.4\%] compared with 63.6\% [38.2\%, 87.3\%] for P1. Furthermore, P2 achieved a lower hard constraint violation rate of 21.8\% [5.5\%, 43.6\%], whereas P1 violated hard constraints in 38.2\% [16.4\%, 63.6\%] of evaluated cases. Conversely, P1 achieved a higher profile acceptability rate of 83.6\% [63.6\%, 100.0\%], compared with 74.1\% [54.5\%, 90.5\%] for P2.

The reported inferential tests indicate that the observed differences in \texttt{JointAccept@1} ($p = 0.7617$), profile acceptability ($p = 0.4062$), image acceptability ($p = 0.2344$), and constraint violations ($p = 0.4062$) are all above the standard significance threshold ($\alpha = 0.05$). Because the evaluation dataset contains 18 independent workload families, the resulting confidence intervals are relatively wide, reflecting statistical variance inherent in small-sample macro-level evaluation. Therefore, these findings represent descriptive differences observed within the development dataset rather than confirmatory proof of statistical superiority.

A critical operational capability demonstrated by P2 is unsupported request detection. When presented with workloads that exceeded available cluster capabilities or demanded libraries not present in the catalog, P2 correctly identified 50.0\% [29.2\%, 75.0\%] of unsupported cases and declined to make an invalid recommendation. In contrast, P1 exhibited 0.0\% unsupported detection, continually attempting to map infeasible requests to nearest-heuristic candidates. In terms of computational overhead, P1 recorded an execution latency of less than 0.5 ms (reported as 0.000 s due to display rounding), while P2 exhibited an observed mean latency of 2.25 ms per request ($p < 0.001$). This confirms that the structured extraction, hybrid retrieval, and constraint filtering in P2 execute within a sub-3-millisecond envelope, introducing negligible overhead into the interactive notebook launching workflow.

\subsection{Candidate retrieval channel ablation}
\label{subsec:retrieval_ablation}

To understand the contribution of each retrieval modality in the hybrid candidate retriever, an ablation experiment was conducted comparing the sparse BM25 channel, the dense semantic embedding channel (\texttt{all-MiniLM-L6-v2}), and the fused dual-channel architecture using Reciprocal Rank Fusion (RRF). Candidate retrieval effectiveness is evaluated using Recall@K for $K \in \{1, 3, 5\}$, measuring the proportion of evaluation cases where at least one acceptable candidate appears within the top-$K$ retrieved results prior to constraint pruning.

Figure~\ref{fig:retrieval_ablation} illustrates the comparative Recall@K curves across the three retrieval configurations.

\begin{figure}[ht]{Candidate retrieval channel ablation across Recall@1, Recall@3, and Recall@5, comparing Sparse BM25, Dense Semantic (all-MiniLM-L6-v2), and Hybrid RRF fusion.}
\centering
\includegraphics[width=0.78\textwidth]{figures/figure_4_4_retrieval_ablation.png}
\label{fig:retrieval_ablation}
\end{figure}

The ablation results highlight the complementary nature of the two retrieval channels. The sparse lexical channel achieved Recall@1 of 46.4\%, Recall@3 of 83.4\%, and Recall@5 of 84.5\%. Because technical notebook requests frequently include exact library names (such as \texttt{"pytorch"}, \texttt{"tensorflow"}, or \texttt{"scikit-learn"}), sparse keyword matching exhibits strong initial precision when users supply precise software identifiers. In contrast, the dense semantic channel achieved Recall@1 of 24.3\%, Recall@3 of 57.7\%, and Recall@5 of 68.2\%, capturing conceptual affinities but occasionally ranking semantically adjacent yet functionally distinct environments too highly.

When fused through Reciprocal Rank Fusion with equal channel weights ($w_s = 1.0, w_d = 1.0, k_{\mathrm{RRF}} = 60.0$), the hybrid retrieval pipeline achieved Recall@1 of 34.1\%, Recall@3 of 69.1\%, and Recall@5 of 77.7\%. Although sparse retrieval alone exhibited higher recall on exact keyword queries, hybrid retrieval provides critical robustness against vocabulary mismatch when users describe workloads conceptually without specifying explicit library names. As demonstrated in subsequent sections, combining hybrid retrieval with deterministic constraint evaluation ensures that semantic candidates are effectively filtered before final ranking, preventing relevance scores from overriding explicit technical requirements.

\subsection{Stream E2}
\label{subsec:e2_robustness}

Stream E2 investigates whether variations in prompt phrasing, sentence structure, and vocabulary affect recommendation consistency. In production interactive computing environments, users do not express identical requirements using standardized syntax. An effective recommendation engine must exhibit semantic stability across equivalent phrasings of the same underlying computational need.

The evaluation evaluates reviewed-equivalent prompt variants grouped under common workload families. The primary metric is the Semantic Robustness Rate (SRR), defined as the macro-averaged proportion of equivalent prompt variants within a workload family that yield an acceptable recommendation. Additionally, worst-case family robustness measures the percentage of workload families for which 100\% of tested equivalent variants succeed. Table~\ref{tab:e2-results} summarizes the robustness metrics observed on the development split.

\input{tables/table_4_3_e2_robustness_results}

The observed overall SRR was 60.6\% [36.3\%, 83.3\%] for P2, compared with 56.8\% [31.8\%, 79.5\%] for P1, representing an observed advantage of 3.8 percentage points. The difference is more pronounced in the worst-case family robustness metric: P2 achieved 45.5\%, whereas P1 achieved 0.0\%. This indicates that for nearly half of the evaluated workload families, P2 consistently selected acceptable environments across every tested paraphrase, whereas P1 failed on at least one paraphrase variant in every single family.

While these results suggest that structured intent extraction and hybrid retrieval provide improved tolerance to linguistic paraphrasing, the findings remain strictly bounded by the evaluated development corpus. The prompt variants represent curated, reviewed-equivalent formulations and do not encompass arbitrary unconstrained natural language, multilingual dialectal diversity, or severe syntactic noise. Furthermore, several category-specific sub-cells (including canonical and Vietnamese formulations) lack verified sample denominators in the report logs and are retained as descriptive development observations rather than rigorous subgroup benchmarks.

\subsection{Cross-metric and trade-off analysis}
\label{subsec:cross_metric_analysis}

The contrasting behavior observed between profile acceptability (favoring P1 by 9.5 percentage points) and image acceptability (favoring P2 by 23.7 percentage points) underscores a fundamental architectural principle: recommendation quality cannot be captured adequately by a single collapsed scalar score.

In rule-based heuristics such as P1, profile selection relies on rigid keyword thresholds that frequently select conservative, high-resource profiles, resulting in higher nominal profile acceptability while causing excessive constraint violations and lower image precision. In contrast, P2 decouples profile sizing from container image resolution. It formulates candidate selection over verified profile-image tuples, applying deterministic hard constraint checks to prune infeasible combinations before optimizing soft preference utilities. Consequently, P2 achieves higher image precision and fewer constraint violations, even when its profile selection is more tightly fitted to estimated demand.

Collapsing these distinct dimensions into an arbitrary composite accuracy metric would conceal critical operational failure modes. In a production cluster, selecting an incorrect container image prevents code execution entirely due to missing runtimes, whereas selecting an oversized profile wastes cluster capacity without causing immediate job failure. Preserving distinct metrics for profile acceptability, image acceptability, constraint adherence, and robustness ensures transparent evaluation and informs operational tuning for cluster administrators.

\section{Kubernetes cluster resource evaluation}
\label{sec:cluster_resource_eval}

\subsection{Stream E4}
\label{subsec:e4_cluster_trials}

Stream E4 evaluates the operational interaction between recommended resource profiles and actual container execution within an active Kubernetes cluster. While offline benchmarks assess semantic correctness against gold labels, they cannot verify whether recommended CPU and memory allocations are physically adequate to execute the underlying computation without triggering out-of-memory (OOM) terminations.

The E4 experiment was conducted within an OrbStack-backed Kubernetes environment (\texttt{orbstack:z2jh-context-demo}), deploying 421 real Pod trials across 20 distinct workload families. Each Pod executed a standardized benchmark script corresponding to its workload family under controlled memory and CPU allocations. \centering

Of the 421 evaluated Pod executions, 413 completed successfully with an exit code of zero, yielding an aggregate trial success rate of 98.1\%. Eight trials were terminated by the Kubernetes kernel due to OOM conditions (Linux exit code 137), resulting in an aggregate OOM termination rate of 1.9\%.

The occurrence of these eight OOM events highlights an important reporting discrepancy in the development documentation. Certain early development reports asserted that P2 guarantees 100\% OOM avoidance. However, empirical cluster telemetry confirms that eight Pods experienced OOM termination under specific stress conditions. In keeping with scientific integrity, this thesis reports the actual observed trial counts (98.1\% success, 1.9\% OOM) rather than repeating theoretical avoidance guarantees. A resource recommendation represents a calibrated configuration based on estimated intent; it cannot provide an unconditional runtime guarantee when workload inputs exceed anticipated parameters.

\subsection{In-container resource sampling and envelope profiling}
\label{subsec:cgroup_sampling}

To capture fine-grained container resource consumption during execution, the E4 runner implements an in-container resource sampler interfacing directly with the Linux control groups v2 (\texttt{cgroups v2}) virtual filesystem. The sampler runs as a concurrent daemon thread inside the Pod, polling \texttt{memory.current}, \texttt{memory.peak}, and \texttt{cpu.stat} at 100-millisecond intervals throughout workload execution.

Upon workload completion or termination, the sampler extracts the cumulative CPU usage delta, peak memory footprint, and kernel memory events from \texttt{memory.events}. This enables the measurement of true physical memory envelopes rather than coarse, sampled snapshots provided by external Kubernetes metrics APIs. Figure~\ref{fig:e4_memory_envelopes} illustrates the locally observed memory envelopes across the evaluated workload families, compared against static profile configurations.

\begin{figure}[ht]{Locally observed memory envelopes (P2 Safe Envelope) compared against Static Small (256 MiB) and Static Large (2048 MiB) profiles across 20 workload families in the E4 experiment.}
\centering
\includegraphics[width=0.95\textwidth]{figures/figure_e4_a_memory_envelopes.png}
\label{fig:e4_memory_envelopes}
\end{figure}

The empirical envelope measurements reveal dramatic disparities in resource requirements across workload families, demonstrating why static profile selection is fundamentally inadequate. Workloads such as \texttt{large\_hash\_map\_allocation} and \texttt{categorical\_encoding} exhibited memory requirements between 384 MiB and 1,792 MiB. When executed under a standard \texttt{Static Small} profile (fixed at 256 MiB), these memory-intensive workloads suffered immediate OOM termination. Conversely, lightweight workloads such as \texttt{streaming\_statistics} and \texttt{sparse\_graph\_traversal} operated safely within a 64 MiB envelope. Forcing these lightweight workloads into a conservative \texttt{Static Large} profile (fixed at 2048 MiB) resulted in up to 96.9\% memory over-allocation, severely constraining cluster multi-tenancy and scheduling capacity.

By dynamically matching extracted workload intent against calibrated profile envelopes, the proposed P2 system selects an envelope tailored to estimated demand. Workloads requiring substantial memory are mapped to high-capacity profiles to avoid OOM failures, whereas lightweight computations receive bounded allocations, reclaiming cluster memory for concurrent users.

\section{Container image capability and storage accounting}
\label{sec:image_capability_and_storage}

\subsection{Stream E5: container image capability probing}
\label{subsec:e5_capability_probes}

Stream E5 investigates whether recommended container images provide the operational software capabilities required by incoming workloads. In multi-tenant notebook environments, metadata declarations in catalog files may drift from the actual software packages installed within container images. Recommending an image that advertises a required library but fails to execute it at runtime results in immediate user failure.

To address this challenge, stream E5 implements an isolated capability verification engine using Docker and an administrator-controlled catalog (version \texttt{2026-08-06.1}). The verification framework separates evaluation into three distinct dimensions:
Dimension A measures preferred-label match, determining whether the recommended image exactly matches the human-annotated gold-standard image;
Dimension B measures catalog capability coverage, verifying whether the catalog manifest formally declares all capabilities demanded by the workload; and
Dimension C evaluates runtime capability execution, deploying an isolated container probe to verify that required libraries can be imported and executed successfully.

Figure~\ref{fig:e5_probe_workflow} illustrates this three-tier verification architecture.

\begin{figure}[ht]{Three-tier container image verification architecture in Stream E5, separating gold-label correctness (Dimension A), catalog metadata soundness (Dimension B), and in-container runtime capability execution (Dimension C).}
\centering
\includegraphics[width=0.95\textwidth]{figures/figure_4_2_e5_probe_workflow.pdf}
\label{fig:e5_probe_workflow}
\end{figure}

In Dimension C, probes execute inside isolated Docker containers with physical memory capped at 1 GiB and execution guarded by an in-container \texttt{SIGALRM} deadline watchdog. Probes that time out or trigger runtime exceptions are intercepted and categorized into an explicit error taxonomy (including \texttt{OOM}, \texttt{IMPORT\_ERROR}, \texttt{ASSERTION\_FAILURE}, and \texttt{SYNTAX\_ERROR}). Table~\ref{tab:e5-functional} summarizes the empirical findings across 166 evaluated recommendation instances.

\input{tables/table_4_5_e5_functional_probes}

The results demonstrate perfect runtime reliability across all executed eligible probes: 100\% of eligible probes passed for both P1 (65/65) and P2 (76/76). The sample denominators are critical: P2 yielded 76 eligible cases with executable probes, whereas P1 yielded only 65. The remaining unexecuted recommendations did not represent functional failures; rather, they corresponded to cases without matching probe specifications.

Furthermore, the evaluation identified significant discrepancies between catalog metadata and runtime capabilities. Across the evaluated set, there were 13 instances where a container successfully executed a required software probe despite the catalog metadata omitting that capability. Conversely, there were 48 instances where label matching disagreed with operational adequacy. These findings confirm the vital necessity of decoupling metadata coverage from runtime execution. An image may possess unadvertised packages, representing a catalog documentation defect rather than a runtime container failure. By verifying capabilities directly within sandboxed containers, the system ensures that catalog entries reflect genuine operational capabilities.

\subsection{Stream E5: compressed OCI layer storage accounting}
\label{subsec:e5_storage_accounting}

Stream E5 also evaluates the storage implications of container image selection by inspecting content-addressed layer descriptors within Open Container Initiative (OCI) image manifests. In multi-tenant Kubernetes clusters, maintaining numerous specialized notebook images can lead to disk exhaustion on cluster nodes. However, container images constructed from standardized base layers share underlying filesystem layers, allowing Kubernetes container runtimes to store and transfer shared layers only once.

The storage evaluation inspected four approved container images on Linux/ARM64: \texttt{minimal-python}, \texttt{scipy-data-science}, \texttt{pytorch-deep-learning}, and \texttt{tensorflow-deep-learning}. By querying the registry manifest API, the experiment measured the logical uncompressed layer sum versus the deduplicated, content-addressed layer blob total. \section{Human interaction evaluation protocol}
\label{sec:human_evaluation_protocol}

\subsection{Stream E3}
\label{subsec:e3_study_design}

Stream E3 is designed to evaluate the human-computer interaction impact of intent-aware recommendation compared with manual environment selection. In standard JupyterHub deployments, users must inspect resource profile tables and image descriptions manually, a process that can introduce cognitive overhead and lead to suboptimal environment choices. Stream E3 formulates a rigorous, within-participant experimental protocol to compare the manual baseline, B0, against the proposed intent-aware workflow, P2.

Under the experimental protocol, participants are assigned a series of representative interactive computing tasks, each characterized by specific workload requirements (such as model training, data analysis, or deep learning inference). To eliminate order effects and learning bias, the protocol implements a counterbalanced Latin square design, alternating the presentation order of B0 and P2 across participants. In both conditions, participants operate over the identical administrator-approved catalog, ensuring that P2 receives no private catalog information unavailable to B0.

The primary outcome metrics defined in the protocol include task completion time (seconds from task presentation to notebook launch), task correctness (proportion of selections satisfying workload constraints), decision confidence (measured via 5-point Likert scales), perceived cognitive workload (measured via the NASA-TLX instrument), and system usability (assessed through the System Usability Scale, SUS).

\subsection{Empirical status and reporting transparency}
\label{subsec:e3_status}

At the current stage of repository development, the E3 testing harness, user interface instrumentation, and experimental protocol have been implemented and verified via automated smoke tests. However, no human participant trials have been conducted.

In adherence to strict academic honesty, this thesis explicitly reports that Stream E3 contains zero participant observations. Consequently, no empirical claims are made regarding reductions in task completion time, improvements in user decision accuracy, decreases in cognitive workload, or superior subjective usability scores.

The absence of human experimental data is an essential distinction. High algorithmic accuracy in offline benchmarks does not automatically guarantee improved human decision-making. Users may misunderstand automated recommendations, override correct recommendations with personal preferences, or find manual selection simpler when catalogs contain very few options. Conducting full human-subject trials under the verified protocol remains an essential objective for future work.
