\chapter{Introduction}

\section{Context and Problem Statement}
Computational notebooks combine executable code, computed results, and explanatory prose in an interactive document. They support exploratory data analysis, teaching, scientific computing, and machine-learning development because a user can move between an idea and its execution without first building a complete application. A notebook service used by a class, laboratory, or organization must also manage identity, isolate sessions, provide storage, and offer environments that remain maintainable over time. JupyterHub provides the multi-user control plane for these services, while a Spawner implementation creates each user's server. In a Kubernetes deployment, KubeSpawner maps a user's server to a Pod and associated resources. Administrators commonly expose a finite set of profiles and container images through configuration such as a profile list \cite{kluyver,jupyterhub,kspawner,z2jh}.

This curated-choice model is operationally important. An administrator can build known images, constrain CPU and memory, decide which accelerators may be requested, and avoid letting each user provide an arbitrary image reference. The same design creates a decision burden at the interface. Users think in terms of work: load a dataset, preprocess text, fit a model, or process images. The platform asks them to select an environment, image, and sometimes resource profile. A person who knows the task but not the catalog internals may choose a profile by name, choose a familiar framework image that is heavier than needed, or select an environment that lacks a required capability.

Intent-Spawner investigates a bounded decision-support layer at this boundary. Its purpose is to map a description of the current task and any explicit constraints to a ranked set of administrator-approved alternatives. It does not replace Kubernetes scheduling, resource admission, quotas, or runtime monitoring. It does not promise to know a workload's peak demand before execution. It seeks to make the profile-selection decision more informed, reviewable, and reproducible while preserving user choice and platform policy.

Let a user request be a description $q$ of an intended computation, possibly accompanied by explicit statements such as a required library, GPU requirement, minimum memory, or forbidden capability. Let $C$ be a finite catalog of administrator-curated profile-image candidates. Each candidate contains descriptive metadata, supported capabilities, resource characteristics, and a reference to an approved image. The system must present relevant candidates without treating semantic similarity as proof of feasibility.

This distinction is central. A candidate can mention a desired framework while failing a hard memory bound. Another candidate can be feasible but rank poorly because a task is described using a paraphrase rather than the catalog's keywords. An unconstrained language model could generate plausible configuration that is not approved, while a fixed rule list can fail on natural variation. A useful recommender therefore needs to separate four operations: interpret intent into structured data; retrieve likely candidates; deterministically enforce hard requirements and policy; and allow the user to inspect and confirm the choice. The final Pod still passes through Kubernetes admission and scheduling, which remain authoritative for cluster state \cite{k8sresources,k8sscheduler,k8sqos,k8sgpu,k8squota}.

The research problem is consequently not general cloud resource optimization. It is a pre-spawn selection problem in a controlled catalog. The proposal is judged across separate dimensions: offline recommendation quality, stability under language variation, human choice and effort, resource-envelope adequacy, and image functionality and storage accounting. Evidence from one dimension cannot substitute for another. For example, an offline label match does not establish that a participant made a better decision, and a container-layer accounting result does not establish savings on a particular cluster's node filesystem.

\section{Research Questions and Objectives}
The thesis follows six research questions defined by the Protocol-v5 experiment plan. They are deliberately framed so that empirical evidence can be collected and interpreted independently.
\begin{enumerate}
\item \textbf{RQ1: Recommendation quality.} Under a frozen candidate catalog and development-independent evaluation split, how does P2 compare with the frozen P1 recommender on workload-family-level candidate quality?
\item \textbf{RQ2: Language robustness.} How does P2 behave when the same workload family is expressed through controlled paraphrases, abbreviations, and language forms?
\item \textbf{RQ3: Human outcomes.} In a within-participant task, does P2 change completion time, choice quality, confidence, perceived workload, or usability relative to ordinary manual profile selection (B0)?
\item \textbf{RQ4: Resource envelopes.} For a declared set of workload families and an eligible Kubernetes environment, how do independently measured safe resource envelopes compare with available static profiles and policy-bounded recommendations?
\item \textbf{RQ5: Image functionality and storage.} Do approved images pass bounded functional probes, and how does content-addressed layer reuse affect logical versus unique layer-byte accounting for the measured catalog?
\item \textbf{RQ6: Optional LLM reranking.} Does a grounded reranking branch meet its predeclared development gate, and, if retained, does it provide enough benefit to justify its added cost and complexity?
\end{enumerate}

These questions do not imply that every hypothesis has been decided. The current consolidated research-analysis package reports INCOMPLETE, and registered confirmatory decisions remain \texttt{NOT\_EXECUTED}. RQ1 and RQ2 have development observations, RQ3 lacks participant observations, and E4/E5 packages are bounded local or development observations. The thesis treats these statuses as part of the result rather than as missing text to be filled by assumption.

The objectives are to: (1) define a safe and auditable pre-spawn recommendation workflow; (2) implement structured intent, hybrid candidate retrieval, constraints, deterministic ranking, trusted catalog resolution, preview, confirmation, and hook integration; (3) define separate experiment streams and provenance requirements; and (4) report the currently available evidence without overstating its scope.

The principal contribution is a systems integration of established techniques at a practical JupyterHub boundary. The work does not claim to invent BM25, dense retrieval, rank fusion, constraint checking, or container-layer deduplication. It composes them into a workflow in which untrusted request text cannot directly become arbitrary Kubernetes configuration. A second contribution is the explicit boundary between a development decision-support feature and the platform's authoritative controls. A third is an evidence-oriented evaluation design that distinguishes semantic workload families from prompt variants and repeated executions. Finally, the repository contains a working prototype and machine-readable experiment harnesses that make later confirmation possible.

\section{Scope and Methodological Approach}
The target setting is a JupyterHub installation in which an administrator owns the candidate catalog and the user is authenticated before requesting a preview. The principal method is P2. B0 is the ordinary manual profile/image selection workflow and generates no ranking. P1 is the existing frozen rule-based comparator. P3 is an optional grounded language-model reranker which was not retained after its development gate. The main text concerns the recommendation service and its interface to the pre-spawn configuration path; it is not an evaluation of the scheduler, node autoscaler, or all of JupyterHub.

The term \emph{context-aware} refers to the current task description, explicit structured requirements, and the current administrator-owned catalog and policy. The implementation is not a longitudinal personalization system. It does not infer user skill from history or inspect notebook contents to rank environments. It does not observe live cluster headroom during P2 candidate ranking. User history, when considered as future work, would require a separate privacy and evaluation design.

Empirical scope is similarly bounded. E1/E2 are development evidence; E4 records local OrbStack Pod/workload observations; E5 records digest-pinned image probes and OCI manifest layer accounting for a small set of images on linux/arm64. E3 has no participants. The statistical-analysis package has audit issues and has not issued confirmatory decisions. Accordingly, this thesis does not claim statistically confirmed improvement over P1, improved user outcomes over B0, generalized resource efficiency, GPU execution, production readiness, or realized storage savings in a multi-node registry or cluster.

The thesis adopts a design-and-evaluation stance. It first defines the system boundary and translates the user problem into explicit functional requirements. It then implements a prototype in the repository and evaluates components through separate evidence streams. This approach is suitable for a systems thesis because a recommender at a pre-spawn boundary must satisfy both software integration requirements and research evaluation requirements. A ranking-only prototype would leave unresolved the question of how the choice is applied, while an implementation-only demonstration would leave the quality and limitations of its recommendations unexamined.

The expected use is assistive. The system should reduce the effort required to understand a catalog, surface the alternatives that plausibly fit a task, and let a user make an informed selection. Administrators continue to define images, resource profiles, and policy. The user remains responsible for confirming the option in the current prototype workflow. Platform controls remain responsible for final admission and scheduling. This allocation of authority is intentional: the recommender has incomplete information about runtime behavior and cluster state, while administrators and users possess different but complementary context.

Several design requirements follow. The method must produce a candidate drawn from trusted data; preserve explicit requirements through filtering; make its suggestion reviewable; handle infeasibility without silently weakening constraints; and reproduce the same order under the same versioned inputs. The evaluation must use comparisons that reflect the task, maintain an independent unit appropriate to each experiment, and report unexecuted conditions explicitly. These requirements connect the technical method in Chapter 3 to the experiment design and claim boundaries in Chapter 4.

\section{Thesis organization}
Chapter 2 introduces notebook infrastructure, Kubernetes resources, resource estimation, intent interpretation, retrieval, recommendation constraints, user-centered evaluation, container images, and related work. Chapter 3 presents the P2 method, its formal ranking problem, trusted-data boundaries, confirmation mechanism, and optional extensions. Chapter 4 describes the prototype implementation and Protocol-v5 evaluation design, then reports available evidence with its provenance and limitations. Chapter 5 discusses the implications and threats to validity, concludes the thesis, and sets out prioritized future work. The five-chapter organization follows the requested LaTeX chapter files; implementation and experiments are integrated into Chapter 4 so that the manuscript remains aligned with that structure.
