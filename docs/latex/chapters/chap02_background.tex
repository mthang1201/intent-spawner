\chapter{Background and Related Work}

\section{JupyterHub and Resource Management}
JupyterHub separates the multi-user service from the individual notebook server. The Hub authenticates users, routes them to their servers, and delegates server creation through a Spawner abstraction. KubeSpawner realizes that abstraction by creating Kubernetes resources for each user. Zero to JupyterHub (Z2JH) packages a common deployment model and supports administrator-defined profiles that map user choices to approved overrides \cite{kluyver,jupyterhub,kspawner,z2jh}.

A profile can bundle a software image with resource requests, limits, storage choices, environment variables, and other server settings. This catalog acts as a policy boundary: the user selects among reviewed options, while the administrator remains responsible for what can be deployed. The default B0 workflow is intentionally retained as the baseline because it represents an existing and operationally useful user experience. Intent-Spawner does not assume that manual profiles are defective. It asks whether an optional translation and ranking step helps users navigate a catalog whose names and technical properties may not match their vocabulary.

The Spawner lifecycle also determines where the method belongs. The recommendation is made before a user's Pod is created, and a stored decision is applied during pre-spawn configuration. The method therefore cannot know the node that will eventually host the Pod or guarantee that the cluster will admit it. This is why Intent-Spawner should be described as pre-spawn decision support, not as a Kubernetes scheduler or autoscaler.

Kubernetes resource requests and limits have distinct roles. Requests contribute to scheduling feasibility and resource accounting; limits bound container use. CPU limits can be enforced through throttling, while memory limit violations can result in termination. Pod QoS classification is also affected by resource configuration. GPUs and other accelerators are typically exposed as extended resources through device plugins, while ResourceQuota constrains aggregate namespace usage \cite{k8sresources,k8sscheduler,k8sqos,k8sgpu,k8squota}.

These semantics caution against deriving resource values from words alone. A phrase such as “large analysis” does not specify a safe memory ceiling. An explicit minimum-memory statement can be represented as a constraint, but a vague workload description is not equivalent to an observed peak. Similarly, the presence of “GPU” in a request is not evidence that a suitable accelerator is available. P2 can filter catalog candidates according to declared capabilities and configured policy; it cannot reserve a live device or override cluster admission. If no catalog entry satisfies an explicit requirement, the correct result is a no-feasible-candidate condition or user-directed manual path, not a fabricated configuration.

Kubernetes will make later admission and placement decisions from current cluster state. A candidate that passes P2 constraints can still fail because of quota, taints, affinity, node pressure, admission policy, registry access, or a race between preview and spawn. The design therefore needs a clear handoff: P2 emits an allowlisted configuration proposal; the normal platform lifecycle remains authoritative.

Resource-management systems often rely on runtime observations, workload history, trial executions, or service-level objectives. Vertical Pod Autoscaling can recommend or apply requests based on observed usage. Autopilot and Resource Central study workload-aware management at larger operational scales. Ernest and CherryPick use sampled runs or optimization to predict performance and identify configurations \cite{vpa,autopilot,resourcecentral,ernest,cherrypick}. These systems demonstrate that resource selection is a substantive systems problem, but their evidence differs from a user's pre-run task description.

Intent-Spawner is complementary in scope. It operates at the moment when the user chooses an environment and may have no profile-specific execution history. It can recommend a curated option based on expressed intent and known catalog metadata, then evaluate whether that option was adequate using independent workload experiments. It must not claim to predict exact demand from intent. The term \emph{safe envelope} in E4 refers to an experimentally declared range under a particular workload, harness, and environment; it is not a universal upper bound for all notebooks with a similar description.

A reliable rightsizing experiment needs to distinguish requests from limits, establish a repeatable workload family, observe resource use under a stated environment, include failures such as OOM kills, and preserve trial-level provenance. Repeated runs are useful to estimate variability and stability. They do not become additional semantic workload families. This distinction is central to the Protocol-v5 unit-of-analysis policy.

\section{Intent and Recommendation Methods}
Intent-based systems describe a desired outcome at a higher level than the mechanism that realizes it. The IETF intent-based networking framework distinguishes intent translation from fulfillment and assurance \cite{rfc9315}. Surveys of intent-based networking identify similar concerns across domains: translating an abstract request, validating it against policy, activating a solution, and evaluating the result \cite{leivadeas}. Natural-language interfaces to system configuration face a related issue \cite{nl2bash}: free-form expression is convenient, but translating it directly into executable commands can yield invalid or unsafe actions.

The Intent-Spawner design narrows the action space. A user describes a workload; the system maps the description to typed fields and selects from a finite catalog. It does not generate arbitrary Kubernetes manifests. The catalog and policy remain administrator-controlled. This makes validation tractable and supports human inspection before the decision is applied. Related work on intent-driven cloud resource design explores translation from goals to resource descriptions \cite{wu}, while P2 focuses on ranking Jupyter environments from curated candidates and preserving a pre-spawn confirmation boundary.

Structured extraction is important even when the original input is natural language. Fields such as required capabilities, excluded capabilities, minimum memory, accelerator requirement, and task tags can be validated and consumed independently. The structured representation creates an explicit place to record uncertainty and source. A guessed capability should not silently become equivalent to a user-stated hard requirement. The actual implementation validates a versioned schema and uses deterministic downstream rules; this constrains, but does not eliminate, upstream interpretation errors.

Sparse retrieval methods such as BM25 score lexical overlap with term-frequency and document-length normalization \cite{bm25}. This is useful for exact technical tokens, library names, and framework identifiers. Its limitation is vocabulary mismatch: a user may describe “table cleanup” while a candidate is indexed under a library name or “dataframe transformation.” Dense retrieval maps text to vectors and can retrieve semantically similar descriptions despite surface variation. Sentence-BERT and Dense Passage Retrieval are prominent examples of learned embedding-based retrieval \cite{sentencebert,dpr}. Dense matching can, however, blur distinctions among technical terms or return semantically related candidates that do not satisfy a mandatory capability.

Hybrid retrieval uses complementary signals. P2 combines BM25 and dense-retrieval rankings, then applies Reciprocal Rank Fusion (RRF). RRF combines ranks rather than requiring the scores from two retrieval systems to share a calibrated scale \cite{rrf}. In a typical formulation, each candidate receives a fused score equal to the sum of reciprocal rank contributions, with a positive smoothing constant $k$:
\[
\operatorname{RRF}(c)=\sum_{r\in\mathcal{R}}\frac{1}{k+\operatorname{rank}_r(c)}.
\]
Here $\mathcal{R}$ is the set of retrieval lists. This is an established rank aggregation technique; the contribution is its use in a controlled recommendation pipeline, not the formula itself.

Retrieval is candidate generation, not final feasibility. The top retrieved candidate may still be invalid under an explicit requirement or policy. P2 therefore applies deterministic constraint evaluation after retrieval and only ranks the remaining feasible set. Retrieval recall and final recommendation quality are separate measurements: low recall limits what downstream ranking can recover, while high recall alone does not imply that the top recommendation is appropriate.

Constraint-based recommenders separate hard requirements from soft preferences \cite{constraintrec}. For Intent-Spawner, hard constraints include requirements that make a candidate unusable, such as an explicitly required framework or accelerator that the candidate does not declare. Soft preferences can express task similarity, preferred resource class, or other non-mandatory compatibility signals. The distinction matters because a weighted score should not allow a strong semantic match to compensate for violating a mandatory safety or capability condition.

After infeasible candidates are removed, P2 produces a deterministic order. A reproducible order requires fixed component versions, stable candidate identifiers, configured ranking weights, and deterministic tie-breaks. Ranking metrics such as Mean Reciprocal Rank and normalized discounted cumulative gain characterize the location of acceptable alternatives in a list \cite{herlocker,jarvelin}. They do not capture whether the user understands a recommendation, whether the environment actually executes the task, or whether the experience is faster.

Decision-support literature emphasizes the allocation of authority between a system and its user \cite{parasuraman,jameson}. Intent-Spawner follows a human-in-the-loop model: it explains the candidate and its attributes, invites confirmation, preserves editing and allowlisted override, and does not spawn solely because a model produced a top result. This control boundary also supports error recovery: a user can reject an unhelpful suggestion before the environment is created.

\section{Evaluation, Human Factors, and Image Storage}
Recommendation systems are not evaluated adequately by ranking metrics alone. User-centered frameworks distinguish accuracy, perceived usefulness, confidence, transparency, satisfaction, and effort \cite{pu,knijnenburg}. For this system, E3 is designed as a within-participant comparison between B0 manual selection and P2-assisted selection. Candidate outcomes include task completion time, correctness or acceptable choice, confidence, perceived workload, and usability measures such as the System Usability Scale \cite{brooke,sauro}.

A crossover design can reduce between-participant variance by exposing each participant to both conditions, but it needs counterbalancing, clear task equivalence, training, and analysis that accounts for participant and task effects. Repeated task variants cannot be treated as independent people. Moreover, consent and privacy safeguards are required because task logs may contain identifying details. No such participants have been measured in the current E3 package. Therefore, this chapter describes the planned construct and instrument, not a usability result.

OCI images are assembled from content-addressed layers described by a manifest. A layered design allows images to share immutable content, but the meaning of “size” depends on what is counted. Summing every layer descriptor occurrence across image manifests gives a logical sum; summing unique digests gives unique layer bytes for that catalog prefix. The two quantities differ when layers are shared or repeated. Docker storage documentation and studies of container distribution discuss this reuse and its operational implications \cite{oci,dockerlayers,harter,anwar}.

Unique manifest-layer bytes are not the same as measured node disk consumption. Runtime snapshotters, unpacked filesystems, compression, garbage collection, local caches, and registry behavior affect actual storage. E5 therefore labels its size domain as compressed OCI manifest layer bytes and reports the target platform. The interpretation remains limited to the measured catalog and does not generalize automatically to a production cluster or to a larger catalog that was unavailable for measurement.

A recommendation benchmark needs a clear definition of a query, a candidate, a relevant set, and the independent unit. If a workload family is written in English, Vietnamese, abbreviated text, and several paraphrases, those variants remain expressions of the same semantic task. Treating each variant as independent would make confidence intervals artificially narrow. The Protocol-v5 design therefore aggregates at family level and uses repeated executions only to characterize execution variability. This is consistent with the general principle that the analysis unit must match the source of independent variation.

For a ranked list, reciprocal rank rewards the position of the first acceptable item \cite{herlocker}. Discounted cumulative gain assigns graded relevance and discounts lower positions; normalized DCG divides by an ideal ranking to permit comparison across queries with different relevant-set sizes \cite{jarvelin}. Hit@K answers whether at least one acceptable option appears in the first K positions. These metrics answer different ranking questions, and none directly measures user value. The primary metric must be chosen before confirmatory execution. Secondary metrics should be reported with their definitions and uncertainty, not selected after seeing which one favors a method.

Paired analysis is suitable when P1 and P2 receive the same workload families. Pairing removes some between-family difficulty variation, but does not remove the need for enough independent families. If several hypotheses are tested, multiplicity control such as Holm's sequential procedure limits family-wise error \cite{holm}. Bootstrap intervals can express uncertainty, but the resampling scheme must preserve the family as the sampling unit \cite{bootstrap}. Small samples and tied outcomes may make conclusions inconclusive; an honest inconclusive result is preferable to a post hoc metric change.

Human studies have a different unit. A participant completing multiple tasks contributes repeated measures, and task order may create learning or fatigue effects. A crossover study should counterbalance condition order, report exclusions, and model participant-level dependence. A timing difference can be practically small even when statistically detectable, while a usability score can summarize perceived interaction without proving task correctness. The constructs should be reported separately. E3 is consequently planned as an independent participant-based stream rather than an extension of offline ranking evaluation.

Resource trials have yet another unit structure. A workload family can be repeated under resource limits to identify failure boundaries, but the trials are nested within family and environment. OOM events are meaningful outcomes, not discarded outliers. Safe-envelope derivation requires an explicit rule (for example, a minimum configuration meeting a declared success and headroom criterion), and should distinguish observed limits from recommended profile policy. CPU throttling, memory peaks, process exit, and measurement coverage should be retained at trial level. The current local run count must not be mistaken for hundreds of independent task types.

\section{Catalog Quality and Research Gap}
A retrieval system can only rank the information represented in its candidate corpus. Catalog metadata therefore affects both relevance and feasibility. Candidate descriptions should identify supported frameworks and libraries, base image, resource profile, accelerator class, and applicable limits with controlled names where possible. If an image can execute a capability that its metadata omits, the system may under-recommend it; if metadata claims a capability that the image lacks, it may recommend a broken environment. The E5 functional probe stream addresses part of this metadata-to-execution relationship, but the current bounded probes do not certify all image functionality.

Metadata maintenance is an operational responsibility. Image updates can alter package versions, image digests, size, and capabilities. A catalog release should bind its metadata to immutable references and be tested before activation. Search-index generation should include its source catalog version and checksum. Otherwise, two runs described as the same P2 configuration may silently differ in candidate content even if code and weights remain fixed. This is why provenance includes catalog and index versions alongside source revision and dataset identity.

Candidate coverage also places an upper bound on recommendation quality. If no approved candidate has a required framework, no ranking algorithm can make the requirement feasible. Adding candidates changes the recommendation space and image-storage footprint and therefore changes the experimental object. Catalog scale experiments should use actual approved images, retain their provenance, and avoid implying results for scales that were configured but not executed. In the current E5 storage study, the catalog contains four approved images; the larger configured scales remain unexecuted.

\subsection{Operational reliability and user trust}
The recommendation endpoint participates in a pre-spawn workflow, so latency, availability, explainability, and recoverability all matter. A user may tolerate a short delay in exchange for a useful comparison, but should not be left with a spinner or ambiguous failure if the retrieval service is unavailable. A sensible interaction can surface a concise explanation of matched task terms, explicit requirements, resource attributes, and any constraint-based exclusion. Such an explanation does not need to expose model internals; it should show the grounds that matter to the user's decision.

Trust is earned by preserving a meaningful override and by making uncertainty visible. If a capability is not verified in the catalog, the interface should not imply that it has been tested. If no candidate satisfies a GPU requirement, the user should see that infeasibility. If a local resource envelope is used to inform a profile, the interface should not label it as a guarantee for workloads it has not measured. These properties connect technical correctness with human control, and they are why preview and confirmation are part of the method rather than decorative interface elements.

The deployment lifecycle also raises reliability requirements. Preview state must survive the route from the UI request to the process handling the spawn hook. A short TTL limits stale decisions, and single-use consumption prevents replay. Multi-replica deployment requires a shared state store or another mechanism that offers equivalent consistency. Failure to resolve the stored candidate should fail closed and provide a recoverable error. These are standard distributed-application concerns, but they are especially visible here because the system must apply exactly the option the user reviewed.

\subsection{Design trade-offs in a curated environment catalog}
A finite catalog simplifies enforcement but creates a coverage trade-off. A very small catalog is easier to secure, test, and maintain; it may not cover specialized libraries or resource combinations. A very large catalog may include more matches but makes image maintenance, user choice, storage accounting, and compatibility review harder. The recommendation system does not eliminate this trade-off. It can help users navigate a catalog, but only administrator decisions can add supported capabilities or approve new images. Catalog expansion should therefore be evaluated jointly for user-facing coverage and operational cost.

There is also a trade-off between semantic flexibility and determinism. Natural language accepts many valid ways to express the same task, while infrastructure configuration requires precise values. Structured extraction can bridge these forms, but each inference introduces uncertainty. The system should interpret softly where only a preference is implied and enforce strictly where a requirement is explicit. The preview gives the user a chance to resolve ambiguous values before creation. This is a domain-appropriate compromise: more flexible than exact keyword matching, yet more bounded than open-ended manifest generation.

A second trade-off concerns resource conservatism. A recommendation that uses more memory than necessary can reduce failure risk but may reduce cluster density or violate quotas. A recommendation that is too small can cause failure, restart, and lost work. Without prior execution measurements, the system cannot calculate this trade-off exactly. Resource profiles should thus be drawn from administrator-reviewed options and backed by measured envelopes where available. The confidence of an envelope depends on workload construction, repetitions, resource measurement, and target cluster conditions. A local synthetic workload can help calibrate a prototype but cannot stand in for every user notebook.

Finally, the system must balance explanation detail with interface burden. Listing every retrieval feature or model score would make the interface harder to read without improving the decision. A concise reason should instead expose task tags, validated requirements, resource settings, and compatibility evidence that matter to the user. If a property has not been verified, that status should be visible. This choice keeps explainability grounded in data rather than presenting a persuasive narrative that may overstate model certainty.

\subsection{Terminology and construct boundaries}
Several terms in this thesis have deliberately narrow meanings. A \emph{candidate} is an administrator-defined profile-image option, not an arbitrary Kubernetes object. A \emph{recommendation} is a ranked candidate list or its top selection before user confirmation. A \emph{confirmed decision} is the option bound to the user's preview state and applied by the pre-spawn hook. A \emph{workload family} is a semantic task grouping that can have multiple prompt realizations. A \emph{prompt variant} is one text form of that family. A \emph{trial} is a repeated execution under a particular environment and setting.

The word \emph{feasible} is local to declared constraints and catalog metadata. It does not mean the Pod is guaranteed to schedule. The word \emph{safe} in a measured resource envelope is conditional on an explicit workload and environment, rather than a universal safety guarantee. \emph{Image functionality} refers to passing the probes that were actually executed, not exhaustive proof that every package works. \emph{Storage savings} in E5 means a difference between logical and unique compressed layer bytes, not observed disk savings on nodes. These definitions prevent terms that sound broad in ordinary language from being read as stronger technical claims than the measurements support.

This terminology also clarifies what different evidence can resolve. E1/E2 can assess candidate relevance and language robustness under a frozen dataset. E3 can assess user outcomes in a particular study population. E4 can estimate resource outcomes under measured workload families and infrastructure conditions. E5 can assess selected functional probes and manifest-layer accounting. A positive outcome in one stream cannot compensate for missing evidence in another because the constructs and units differ.

\subsection{Research gap and synthesis}
Adjacent work provides notebook service primitives, cluster resource control, telemetry-driven rightsizing, intent translation, retrieval, constraint-aware recommendation, user evaluation, and image distribution. The repository-informed gap is a narrow integration question: how can workload language be mapped to a small approved Jupyter environment catalog before spawn while retaining deterministic policy enforcement, user confirmation, and evidence boundaries?

P2 addresses that question as a bounded decision-support system. Its architecture joins typed intent, hybrid retrieval, hard feasibility, deterministic preference ranking, trusted candidate resolution, and a stored confirmation. Its evaluation deliberately avoids collapsing distinct claims into one accuracy score. The method is positioned as a practical prototype whose recommendation and operational consequences require further confirmatory evaluation. No current result establishes that it improves all relevant outcomes or that its behavior transfers to every JupyterHub catalog.
