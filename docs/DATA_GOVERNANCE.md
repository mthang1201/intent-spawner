# Data Governance

## Scope

This repository uses generated synthetic benchmark data and a local JupyterHub
demo. It does not require a sensitive dataset, a raw user notebook, or a user
history store.

## Input Handling

The proposed spawn form accepts intent text, a dataset-size hint, and optional
code context. The inline recommender evaluates these values in memory. It copies
only the resulting profile, matched-signal explanation, and normalized dataset
size to the spawned pod. It does not copy raw intent or raw code context to pod
environment variables, annotations, or recommender log messages.

JupyterHub and Kubernetes still process operational identifiers needed to run a
server, such as the authenticated demo username and generated pod name. Do not
export those logs or Kubernetes objects as research data without sanitization.

## Stored Repository Data

- `benchmarks/workloads.yaml` contains researcher-authored synthetic prompts,
  feature hints, seeds, and expected profile bands.
- `benchmarks/workload_runner.py` generates data in memory. Its temporary CSV is
  deleted when the process exits.
- No `.ipynb`, external dataset, raw code snippet corpus, credential, user ID,
  cluster node name, or machine-specific capacity snapshot is tracked.
- `helm/generated-values.yaml` is ignored because it contains machine-specific
  local node capacity.
- No experiment result set is currently merged.

## Credentials And Access

The demo uses JupyterHub's DummyAuthenticator without a committed shared
password. Any non-empty password is accepted. This is intentionally insecure:
keep the service on an isolated local cluster and access it only through local
port forwarding. Do not deploy these values to a shared or production system.

## Future Experiment Rules

If comparative experiments are added:

1. Store derived signal labels rather than raw notebooks or pasted code.
2. Replace usernames, pod UIDs, node names, hostnames, and cluster context names
   with run-scoped pseudonyms before committing evidence.
3. Record the transformation and the fields removed.
4. Preserve immutable raw technical outputs only in access-controlled storage;
   commit sanitized evidence or aggregate metrics.
5. Define retention and deletion dates before collecting any participant data.
6. Obtain ethics/consent approval before using real user prompts or history.

## Licensing

All benchmark data is generated by repository code; each workload declares
that no external dataset license applies. This is a provenance statement, not a
license grant. The repository has no project software license file, so
redistribution rights remain unresolved and must be decided by the author.
